## 1. 这一轮做了什么

### 1.1 一个真事故：鼠标卡在按下状态

用户报"鼠标黏在 SuYou 上能拖着动"。

- **成因**：`SendMouseButton` 是 `mouse_event(DOWN) → Sleep(40ms) → UP`。
  进程若在 DOWN 与 UP 之间被 `TerminateProcess` 杀掉（宿主的超时兜底正是 `child.kill()`），
  UP 永远不执行，而 Windows 不会替谁松开鼠标。
- **三层兜底**：helper 记账（只松自己按下的键）+ `ProcessExit`；插件在超时分支补发一次
  `dsc.exe release`；代价（会把用户自己按的键一起松开）写进错误文本。
- 补发只放在超时路径：`hold` 是故意按住不放的。

### 1.2 视觉兜底（外部评审的"轻量版"）

方案改了一处：**不打包 OCR**，改用 Windows 自带的 `Windows.Media.Ocr`——"让别人用自己的机器 OCR"。

实测（本机，中文 Windows，零安装）：

```
zh-Hans-CN   688x1055 截图 →  13 行， 98ms
             1941x1242 截图 → 42 行，290ms
```

新增两个工具：

- `desktop_visual_candidates(hwnd, shotId, query?, region?)`：把**已登记的截图**送 OCR，
  返回候选（不透明 ID + 图片内坐标）。不重新截图；明确写"文字锚点不证明可点击"。
- `desktop_click_candidate(hwnd, shotId, candidateId)`：坐标由插件换算，
  **发输入前复查那块像素**；点击仍走原有链路（白名单/几何/急停/落点归属）。

### 1.3 验收 8 条的真实状态

## 2. 踩到的坑（都留了注释与测试）

### 2.1 复查余量 12px → 误拒率 100%

候选「剩余流量」旁边是实时流量计数，12px 余量把计数器框进来，于是**每次复查都判"内容变了"**。
改成 4px，并把"真实误拒率要靠真实任务统计"写进注释。

### 2.2 基线与点击用了不同的框

基线用 `box`、点击用 `box+4` —— 两块像素根本不同，好端端的点击被判"变了"。
现在共用 `visualRoi()`。

### 2.3 从未查清的异常：同像素、不同指纹

```
image_hash(整张截图, 区域 54,122 171x34)   = ce0f8519841ee66a
image_hash(同一块单独存的 PNG, 0,0 171x34) = f3c585f08d4d2c6c
PIL 逐像素比对这两份图                     = diff bbox None（完全相同）
```

整窗比对永远一致，**只有局部区域**会错。逐条排除：

| 假设 | 怎么排除 | 结果 |
|---|---|---|
| 鼠标光标 | 把光标移出区域再算 | 指纹不变 |
| `DrawImage` 插值/半像素 | 改用 `Clone` | 不变 |
| `LockBits(rect)` 行跨度 | 改成锁整图 + 手工偏移 | 不变 |
| PNG 往返 | 抓屏→存 PNG→读回→算 | 不变 |
| 抓屏路径不同 | PowerShell 独立抓同一块，与截图逐像素比 | 完全相同 |

**根因仍未钉死。** 绕过去的方法：复查基线改成**从屏幕取**（列候选时抓一次、点击时再抓一次），
两边同源。

### 2.4 动画检测做了又删

想借 Playwright 的 **Stable** 检查（三次采样、间隔 200ms，全一样才点）。
实测：夹具每 60ms 翻一次字，**三次采样仍能返回同一个指纹**（怀疑 WinForms 计时器在
`DoEvents` 循环里的实际节拍远慢于 Interval，未证实）。

一个"看着在检测动画、实际经常漏"的机制比没有更危险——会让人以为"在动的东西点不下去"。
删掉，只比一次，限制写进文档。

### 2.5 测试自身的三个假象

- **OCR 把 `I` 读成方块**：`CLICKHERE` → `C L □ C K H E R E` → "没取到候选"。夹具改用 `BUTTON`。
- **截图拍到遮挡者**：第一次跑，`desktop_screenshot` 拍的是**我自己这个 DSH 窗口**（它盖着 SuYou），
  OCR 出来的候选全是我聊天记录里的字（"把78做完吧"）。工具其实早就有遮挡警告（五点采样），
  是测试没读返回文本。
- **最小化残留窗口**：SuYou 除主窗口外还留一个 `237x39 @(-32000,-32000)` 的隐藏小窗。
  按"第一个 Tauri 窗口"取 → 对着不存在的画面截图 → 得出"没有候选"。改成按面积挑。

## 3. 第 4 条为什么只有源码级断言

预检 → `verifiedImageOf` → `probeOcr` → `runOcr` → 复检，**中间一个 `await` 都没有**，
而 `runOcr` 用 `spawnSync`（阻塞事件循环）。所以**今天这个竞态不可达**：
没有任何并发调用能在这期间把观察作废，另一个 DSH 实例又有自己的 `recentShots`。

这段检查是给未来上的保险——一旦 OCR 改成异步 worker（这是合理做法，`spawnSync` 会阻塞插件
100~300ms，连 `desktop_list_windows` 都进不来），竞态就真实存在。

我不想写一个 `sleep(200)` 撞竞态的假测试：那种测试时红时绿，还会让人以为"验过了"。

## 5. 这轮去 GitHub 找到的东西

> 按"能不能直接解决我们卡住的问题"排序。

### 5.1 pixelmatch —— 精确指纹该换成"容差像素差"

[mapbox/pixelmatch](https://github.com/mapbox/pixelmatch)：几百行、零依赖、MIT，
输入是裸像素数组。关键设计：

- `threshold`：**每像素**的感知色差（OKLab + HyAB），不是"差异占比"；
- `includeAA`：能识别并忽略**抗锯齿像素**（这正是"同一块像素在不同合成路径下略有差异"的来源）；
- `windowSize: N`：返回任意 N×N 窗口内最大的差异像素数，而不是总数——
  用来滤掉 GPU 抖动/子像素抗锯齿造成的散点噪声，同时抓住"真实回归通常是一块紧凑区域"。

**对我们的意义**：现在的"指纹相等"是最脆弱的比较器（§2.3 的异常、§2.1 的误拒都源于此）。
换成容差比较可以同时解决两件事。我们已经有 `image_hash`/`region_hash` 两个命令，
可以再加一个 `region_diff`（载入基线 PNG + 抓屏 + 返回差异像素数/占比/最大色差）。

### 5.2 cua 在 Windows 上用 PrintWindow 抓窗口

[trycua/cua 提交 876d48d](https://github.com/trycua/cua/commit/876d48d20db82b837435c40ee17a3cf1ee1c4204)
（`fix(cua-driver-rs)(windows)(capture): size PrintWindow buffer to GetW…`）——
他们是 **`PrintWindow` 抓窗口自身内容**，不是 `CopyFromScreen` 抓屏幕那块。

**对我们的意义**：§2.5 的"拍到遮挡者"是他们从设计上就没有的问题。
我们现在的做法是"检测到遮挡就警告"，改成 `PrintWindow(PW_RENDERFULLCONTENT)` 是
"从一开始就抓窗口自己"。风险：Chromium/游戏/DirectComposition 内容可能黑屏或空白，
需要实测 + 保留 CopyFromScreen 回退。

### 5.3 openadapt-capture 的"证据模型"

[OpenAdaptAI/openadapt-capture](https://github.com/OpenAdaptAI/openadapt-capture)（MIT）记录
鼠标键盘 + 屏幕 + 无障碍数据，其中四条设计直接对应我们的痛点：

| 他们的做法 | 我们的对应物 | 差距 |
|---|---|---|
| `action.screenshot` **和** `action.after_screenshot`（动作前后各一帧） | `observeAfter` 只有"后" | 缺"前"帧；候选复查其实需要它 |
| `capture-artifact-manifest.json`：每个文件的 size + SHA-256，再加 terminal 记录覆盖 manifest | 只有单图 `pngSha256` | 没有"整批观察"的完整性清单 |
| 坐标可以落在**窗口自己的像素**（`window={"owner": ...}`） | `space:'window'` 分支 | 一致 |
| `structural_observation`（UIA 的 role/name/bounds/actions）**从像素里猜的一律不存** | 我们的候选也是 `role: unknown` | 一致 |

**对我们的意义**：`action.before + after` 和"manifest"这两条值得抄；其余我们已经在做。

### 5.4 OSWorld / 评测方法论

[xlang-ai/OSWorld](https://github.com/xlang-ai/OSWorld)（`DesktopEnv` 的 metric 评估）
是桌面 agent 的标准评测框架：每个任务自带 **`getter` + `metric`**（检查文件、检查配置、
检查页面内容），而不是"看起来对就算过"。

**对我们的意义**：§4 第 1 条（真实任务对照）缺的就是这个形状：**每个任务要有一个
可自动判定的成功条件**，否则"成功率"只能靠人肉看。最小可行版本：
在 SuYou 上定 3 个任务（切页、读某个数值、点一个按钮后出现某元素），
每个任务写一个 getter（读树/读像素），然后跑两组：截图直点 vs 候选兜底。

## 6. 想请评审回答的问题

1. **§2.3 的异常还值得继续查吗？** 还是直接改用容差比较（§5.1）把这类差异整体吸收掉？
2. **容差比较的阈值怎么定**：每像素色差（pixelmatch 默认 0.1）+ 允许百分之几的像素不同？
   还是要 windowed（防散点噪声）？
3. **截图改 PrintWindow 值不值**：一次性解决遮挡，但 Chromium/游戏可能黑屏，需要双路径 + 回退。
4. **观察证据要不要做 manifest**（openadapt 那样）：每个 shot 的 size+SHA256 汇总成一个清单？
   我们现在只有单图 sha256，防不了"文件被换掉但记录还在"。
5. **异步 OCR 值不值**：消掉 100~300ms 阻塞，同时让第 4 条变成可测。代价是管道协议/超时/父进程退出。
6. **任务级对照的最小可行设计**：SuYou 三个任务 + getter 够不够？要不要换一个更能代表真实使用的目标应用？
7. **视觉路径的去留**：在拿到对照数据之前，它应该默认开启、默认关闭，还是只在树读不到时提示"可以试试"？
