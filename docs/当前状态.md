## 四、这次踩过并排除的假设（**不要再走**）

按时间顺序，全部经过实测排除：

| # | 假设 | 排除依据 |
|---|---|---|
| 1 | 我把鼠标代码改坏了 | 同一份 exe 换个位置就能用 |
| 2 | 坐标空间 / DPI 问题 | 屏幕读数正确（2240x1400） |
| 3 | 进程在错误的桌面上 | `CompareObjectHandles`（kernelbase.dll）判定同一对象 |
| 4 | AppContainer 沙箱 | 双方 `IsAppContainer` 都是 0 |
| 5 | 完整性级别 / 提权差异 | 所有进程都是 `ElevationType=3` |
| 6 | 作业对象 UI 限制 | `UIRestrictionsClass = 0x00000000` |
| 7 | `BlockInput` 压制 | 解除后仍无效 |
| 8 | 目标是 Electron / 打包应用 | 同一目标窗口，换 helper 位置就能用 |
| 9 | 合成前台切换导致输入被压制 | 是表象之一，不是根因 |
| 10 | shell 启动链 | 插件直接 spawn（无 bash）同样失败 |
| 11 | 进程存活时间 | 单进程 12 秒内 6 轮全部失败 |
| 12 | 目标窗口的创建上下文 | 用 explorer 启动的干净记事本做目标，仍失败 |

**方法论上真正错的三条**（这三条让我绕了很久）：

1. **读 `SetCursorPos` 之后的 `GetLastWin32Error()`** —— 该 API **不设置** last-error，读到的是上一个 API 的残留值（实测出现过 `2`/`203`/`0`/`5`，全是假的）。**判据必须用"光标实际位置"。**
2. **把"返回值"当"效果"** —— `{"ok":true,"typed":6}` 只说明发出去了，不说明到了。**必须读回验证。**
3. **把一次观察推广成环境规律** —— 沙箱里报过一次 `ERROR_FILE_NOT_FOUND`，我写成"本环境阻断输入注入"并写进 README，结果把两个真 bug 都"解释"掉了。

## 五、改动前请先看这几条

**1. `MoveCursorAbsolute` 用 `SetCursorPos`，鼠标按键用 `mouse_event`。**
不要改回 `SendInput` —— 实测在这一环境下 `SendInput` 被接受但无效。

**2. 所有输入类操作前必须过 `RequireActivated`。**
它做三件事：AppContainer 自检、完整性级别检查、窗口激活。
**去掉任何一件都会让"注入静默失效"重新伪装成环境限制。**

**3. 最小化窗口的 `IsWindowVisible` 仍返回 True。**
UIA 会给 `-32000` 级别的哨兵矩形（实测见到 `-47976`）。
`Snapshot.cs` 和 `CmdClickElement` 都有拒绝逻辑，不要删。

**4. 密码字段必须掩码。**
WinForms 的 `UseSystemPasswordChar` 文本框，UIA **会把明文当 Name 报出来**，
而 Name 会进模型上下文。`Snapshot.cs` 里有处理。

**5. 树遍历必须有界化。**
`BoundedWalk` 的三重上限 + 环路检测是防挂死的。环路检测是**必须的**
（provider 可以把祖先当子节点报回来）。

**6. `set_value` 的回读校验不要删。**
`before`/`after`/`verified` 是唯一能证明"值真的变了"的手段。

## 八、会话级授权：已实现并端到端验证（2026-10-14 晚）

### 机制

DSH 自带 `approval` 服务与 `agents` 服务，把它们接上即可：

```
approval.request({ agent, toolName, reason })
  → 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
    只有 'allowed-once' 是授权
```

判定顺序：**静态白名单 → 本会话已授权 → 问用户**。
所有异常路径（无 answerer、回调抛错、无会话上下文）一律按拒绝处理。

授权绑在**会话 id** 上，会话一换自动失效——**不需要"记得撤销"这个动作**。
另有 `desktop_revoke_grants` 用于中途主动收回。

### 端到端验证（全部通过）

```
① 插件从 bundle 加载          ✅ 12 个工具注册（含 desktop_revoke_grants）
② bundle 的 inject 生效        ✅ 无需手改 profile
③ helper 自动解析              ✅ node_modules/dsh-desktop-control/bin/dsc.exe
④ 操作未授权应用 → 弹询问       ✅ 用户同意后白名单出现该应用
⑤ 同意后操作真的执行            ✅ 截图确认文字进入文档正文
⑥ 同一应用第二次不再询问        ✅ 会话级授权被记住
⑦ 授权不扩散到其它应用          ✅ 点设置窗口仍走询问流程
```

**⑤ 的判据**：向记事本注入 `会话授权跑通了：这一行是注入写入的`，
截图显示它夹在文件原有内容中间（不是"返回 ok 但没效果"）。

### 过程中发现并修掉的两个真 bug

**1. 复制了过期的 `toolset.mjs`。**
仓库里有两份：`server/toolset.mjs` 是源头（与 MCP 服务器共用），
`plugin/toolset.mjs` 是随包副本。手工复制时抄了副本，于是"部署了、重启了、
测试了"，跑的还是旧代码——报错是旧的 `WhitelistEmpty`，看起来像功能没生效。
**已加 `tools/sync-plugin.sh`**：从源头构建副本、同步、并逐文件校验哈希，
还专门断言"部署的那份含不含会话授权代码"，让同类错误在同步时就报出来。

**2. `desktop_click` 缺范围检查，白问用户一次授权。**
点击用的是**桌面绝对坐标**，而授权只按 `hwnd` 校验。于是"hwnd 是记事本、
坐标却落在 DSH 窗口里"这种组合会先弹询问、再被 helper 的 `WindowFromPoint`
挡掉——**实测因此让白名单里多了一个用户其实没打算放行的应用**。
现在先做范围检查，坐标不在窗口内就直接拒绝，**不触发授权询问**。

### 一个仍然存在的观察

`desktop_list_windows` 的提示文案仍写着"当前白名单为空——只能观察"，
而实际已有会话授权机制。这是**文案没跟上**，不是功能问题：
拒绝逻辑已经在 `toolset.mjs` 里统一走 authorize()。

## 九、ESC 强制退出：已端到端验证（2026-10-15）

**完整链路、六类踩过的坑、通用教训，见
[ESC强制退出-完整链路.md](ESC强制退出-完整链路.md)。**

七步验证结果：

```
① 插件加载 v1.0.1               ✅
② 闸门路径在工作区内             ✅  D:\dsh workspace\.desktop-control\halt
③ desktop_indicate 开状态        ✅  光带 + 逃生条
④ 按物理 ESC                    ✅
⑤ 两个进程都退出                 ✅
⑥ 变更性操作被拦                 ✅  "已被急停"，且不弹授权询问
⑦ stop --clear 后恢复            ✅
```

**⑥ 是最有分量的一条**：不只是界面消失，dsc.exe 真的拒绝执行了。

**一条通用教训**（今天在同一个错误上栽了四次）：
**得出"环境不行"之前，先用最小可复现程序把变量压到只剩一个。**
四次错误结论分别是：注入被阻断（真因是 exe 在工作区目录）、
键盘钩子不触发（真因是窗口没被激活过）、日志丢失（真因是沙箱禁止写工作区外）、
闸门拦不住（真因是我的测试没带 DSC_HALT_GATE）。

**补充（同日稍晚）：实机演示通过。**

不是自测，是**助手真在连续操作记事本、人按物理 ESC 打断**：

```
打字【1】 → 已输入 15 字符                     ✅
打字【2】 → 已输入 18 字符                     ✅
打字【3】 → 已被急停：闸门文件存在，拒绝执行    ← 人按了 ESC
```

证据链：钩子日志 `vk=0x1B`、闸门时间戳、进程退出、记事本标题出现 `*` 修改标记
（证明前两段真写进去了）。详见 [实机验证-ESC打断操作.md](实机验证-ESC打断操作.md)。

**演示时踩的一个坑值得记**：助手"在等待"看起来和"被停住"一模一样。
所以演示必须让助手**真的在干活**，否则 ESC 有没有用根本看不出来。
