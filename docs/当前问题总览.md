## 一、未解的问题

### 1. 鼠标注入完全无效（最严重）

**现象**：`SetCursorPos` 与 `SendInput`（相对 / 绝对 / 绝对+VIRTUALDESK）全部无效。
判据是**读回光标实际位置**，不是返回值：

```
起始光标 = (2111,579)
目标(400,300)   → 实际(2111,579)  ❌
目标(900,500)   → 实际(2111,579)  ❌
目标(1400,800)  → 实际(2111,579)  ❌
目标(600,200)   → 实际(2111,579)  ❌
目标(1100,900)  → 实际(2111,579)  ❌
目标(300,400)   → 实际(2111,579)  ❌
到达 0/6
```

**已排除**：桌面身份（WinSta0\Default，与 `OpenInputDesktop` 同名）、会话（同为 44）、
作业对象 UI 限制（`UIRestrictionsClass = 0`）、AppContainer、提权（所有进程都是
ElevationType=3 Limited）、`BlockInput`、DPI（awareness 生效，屏幕读作 2240x1400）。

**间歇性证据**：同一段代码、同一台机器，在某些时刻有效（实测过 `SetCursorPos(400,300)`
命中、按钮被点击 4 次），在另一些时刻完全无效。**触发条件未确定。**

**一个未验证的对照**：Codex 也用 `SendInput`，用户认为它能操作鼠标，但**实际上没有验证过**
——用户的原话是"叫他直接开启这个功能，他说开启了，但我的屏幕和鼠标都没有反应"。
所以 Codex 的鼠标很可能也动不了。**这个对照值得做一次**：让 Codex 执行一个明确需要
移动鼠标的动作，肉眼确认光标是否移动。

### 2. 键盘注入在 Electron 应用上无效（待确认）

**现象**：往 DSH 自己的输入框注入 `"XYZ123"`，命令返回 `typed=6`，
**截图显示输入框是空的**（只有占位文字）。

**但结论不确定**，因为我说不出这两者的区别：

```
树里没有输入框  →  Electron 默认关闭无障碍？
                →  还是字没送进去？
```

**而且更可能的解释是：我只激活了窗口，没把焦点放进输入框。**
再点击输入框那一步失败了（因为问题 1），所以焦点始终没到位。

**验证方法**：在 Chrome/Edge 的地址栏里试——那是普通 Win32 窗口的子控件，
如果键盘能进地址栏但不能进 Electron 的输入框，结论就清楚了。

### 3. 同一段代码，点自己的测试窗口成功、点真实应用失败

```
✅ WinForms 测试窗口（我编译的）→ click_element 成功，按钮文字 "点了 4 次"
❌ 记事本（WindowsApps 打包）  → SetCursorPos 失败
❌ 腾讯视频（Electron）        → SetCursorPos 失败
❌ DSH 自己（Electron）        → SetCursorPos 失败
```

**令牌特征完全相同**（都是 `提升类型=3`、非 AppContainer、同会话），
所以不是完整性级别差异。**未解。**

## 二、已修的问题（本轮）

| 问题 | 修法 | 验证 |
|---|---|---|
| 最小化窗口 `IsWindowVisible` 仍返回 True，导致 UIA 给出 -47976 哨兵矩形，算出 (-47886,-47880) 这种点击点 | 单独判断最小化 + 拒绝哨兵坐标 + 说明原因 | 最小化 → helper 全自动还原+激活+点击 → "点了 4 次" |
| 输入前不激活目标窗口，`SetForegroundWindow` 失败后仍硬注入 | 加 `WindowActivator`，所有输入操作前自动激活，失败即拒绝 | 见上 |
| 无完整性级别检查 | 照 Codex 加 `RequireIntegrityOk`，目标 IL 更高时拒绝 | 不误伤同级目标（记事本键盘输入成功） |

## 三、我自己的方法错误（教训）

这几条导致的返工比技术问题本身更多。

### 1. 把"返回值"当"效果"

`desktop_type` 返回 `{"ok":true,"typed":6}` 只说明**我发出去了**，
不说明**字到了**。补上读回验证之后才第一次真正区分开这两种情况。
（用户早就提示过"没看你动鼠标"，我当时没领会。）

### 2. 读不设置 last-error 的 API 的错误码

`SetCursorPos` **不设置** last-error。我却在它后面调 `GetLastWin32Error()`，
于是读到的是**上一个 API 留下的陈旧值**：`2`、`203`、`0`、`5` 都出现过。
**我据此报过三个不同的"根因"，全是假的。**

**判据应该是"光标实际位置"，不是错误码。**

### 3. 把一次观察推广成规律

沙箱里 `SetCursorPos` 报过一次 `ERROR_FILE_NOT_FOUND`，我把它写成
"本环境阻断输入注入"，还写进了 README。这条"规律"随后把两个真 bug
（SendInput 绝对坐标被 DPI 再缩放、`(byte)` 截断中文）**都"解释"掉了**，谁也没再查。

### 4. 只在自己造的窗口上验证

我的测试窗口是 WinForms，**树完整、注入正常**——是唯一一种什么都通的类型。
真实应用（Electron / WinUI 打包）树都是残的：

| 应用 | 框架 | 树元素数 |
|---|---|---|
| 我的测试窗口 | WinForms | 9（有 aid、有 value） |
| Store 记事本 | WinUI 打包 | 12（全无名 Pane） |
| DSH 自己 | Electron | **4**（无输入框） |
| 腾讯视频 | Electron | **2** |

**我一直在用"最容易成功的靶子"证明"功能正常"。**

### 5. 在诊断上花的时间多于修复

用户说过"回顾代码"，我却继续写新的诊断程序。写过的诊断程序已有十几个
（`HookTest`、`HookBoth`、`HookDiag`、`BindVerify`、`TargetProbe`、
`RawInputTest`、`CursorTruth`…）。**部分程序本身还有 bug**（建窗口失败、
双重 `FreeHGlobal`、`GetWindowThreadProcessId` 重载错），
导致跑出无效数据，还得再花时间判断"这个 0 是真的吗"。

## 五、本机实测否定、不要照抄的

| Codex 的做法 | 本机实测 |
|---|---|
| `SetThreadDesktop(输入桌面)` | **有害**：绑定后注入从"被接受但无效"退化为"拒绝访问" |
| `CompareObjectHandles` 判桌面身份 | **本机 kernel32 无此导出**，P/Invoke 直接抛 `EntryPointNotFoundException`，且异常连 `ToString()` 都失败，程序哑崩 |
| 低层键盘钩子做 ESC 急停 | 钩子装得上、句柄非零、消息循环正常，**回调一次都不触发**（连自注入的键都收不到） |
| 依赖 `SetCursorPos` 的 last-error | 该 API 不设置 last-error |
