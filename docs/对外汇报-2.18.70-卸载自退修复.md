# 2.18.70：卸载自退修复（上一版修错了对象）

> 你这轮的 §2 是全场最有价值的一条：**我验证了"心跳断了会自退"，却没验证"心跳会不会断"**。
> 你杀掉两个进程后心跳仍在刷新，直接证明了写心跳的是 DSH 里残留的定时器。

---

## 1. 真实原因

上一版是这么设计的：

```
插件 setInterval 每 5 秒写 fx.heartbeat
  ↓ 插件卸载后……
fx/guard 看到心跳停止 → 自退
```

问题在第二条：**HMR 卸载不走 `dispose`**，`clearInterval` 从来没被调用。
于是定时器留在宿主进程里继续写，心跳永不停止，自退条件永远不成立。
你观察到的两个后果都成立：孤儿进程 + 每 5 秒写盘的泄漏。

## 2. 修法：不要定时器

心跳只在**真实桌面操作**时写一次：

```js
// touch() 里，每次工具调用写一次
writeFileSync(fx.heartbeat, Date.now())
```

没有任何 `setInterval`。所以"插件不再被使用"就等于"心跳过期"：

```
最后一次使用 → 25 秒后 fx 恢复光标并退出
              → guard 同时（同一判据）恢复并退出
```

- **不需要 dispose 被调用**
- **不需要谁记得 kill**
- 代价：空闲 25 秒后进程退出，下次操作会**重新拉起**（实测 1.8 秒内恢复）

## 3. 证据

新增 `tools/test-cursor-idle-exit.mjs`，它测的正是我上一版漏掉的那件事——
**插件照常加载、但不再有任何操作**：

```
✓ dsc-fx 已启动
✓ 心跳已写入
✓ 心跳没有被后台定时器继续刷新     ← 上一版会在这里失败
✓ dsc-fx 在无操作后自行退出（24 秒）
✓ dsc-guard 也已退出
✓ 再次调用后 dsc-fx 重新启动
```

原有的 `test-cursor-orphan.mjs`（只停心跳）也仍然通过。

## 5. 卸载文档现在的说法

> 卸载后等 25 秒：两个进程会自己退出并恢复光标。
> 若 25 秒后仍在（例如宿主被强杀），手动 `taskkill /IM dsc-fx.exe /F` 与
> `taskkill /IM dsc-guard.exe /F`，**顺序无所谓**。

上一版写的"等 25 秒即可"在机制失效时是误导——这版机制真的成立，测试也盯着它。

## 5.5 你指出的升级陷阱（已写进文档）

从**带定时器的早期版本**升级到本版时，**必须重启 DSH**：旧实例的 `setInterval` 还活在宿主进程里，
会继续写 `fx.heartbeat`，于是新自退机制看起来完全没生效。你那次"重启前心跳仍在写、重启后正常"
就是这条。文档里已经写成硬要求，不是可选项。

## 6. 仍然没解决

- HMR 卸载不触发 `dispose` 这件事本身没有改变（那是宿主行为）。现在的设计**不依赖**它。
- 指示灯那个 `_idleTimer` 是同类风险（卸载后仍可能在跑），但它只操作已消失的进程句柄，
  影响面是"多空转几次"，没有 `dispose` 也确实清不掉——已记在待办里。
