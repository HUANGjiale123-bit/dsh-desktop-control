# 需要指点的问题：会话隔离、输入串行化、错误分类、分段计时

这份写给能看代码的人。每节给出**现状代码**、**我卡在哪**、**我试过/想过什么**、
**具体想问什么**。仓库在 `D:\dsh workspace\dsh-desktop-control`。

背景：这是个 DSH 插件，让模型能观察和操作 Windows 桌面。架构是
`plugin/index.mjs`（工具注册、指示层、截图登记）→ `server/toolset.mjs`
（授权、坐标换算、helper 调用）→ `helper/src/Program.cs`（`dsc.exe`，
真正的 UIA 与输入注入）。`plugin/` 下的三个 mjs 是 `server/` 的拷贝，
由 `tools/sync-plugin.sh` 同步。

## 一、会话隔离：grants、闸门、指示层现在都是全局的

### 现状

`server/toolset.mjs:86`：

```js
/** 本进程内已被会话授权放行的应用。键是应用名，值是授权来源说明。 */
const grants = new Map()
```

它在 `createDesktopToolset()` 内部，而 `plugin/index.mjs:544` 在 `apply()`
里只创建一次：

```js
const set = createDesktopToolset({ ... })
```

所以插件是 profile 级单例，**所有会话共用这一份 `grants`**。

闸门同样只有一个文件（`plugin/index.mjs:391` 解析后缓存）：

```js
if (_gatePath === null) _gatePath = resolveGatePath()
```

指示层（蓝色光带 + 逃生条）是一个 `dsc-esc.exe` 进程，也只有一个。

### 由此产生的具体后果

1. 会话 A 授权 notepad 后，会话 B 直接就能操作 notepad，不会再问。
2. 会话 A 按 ESC 拉了闸门，**会话 B 的工具调用全部被拒**（`RequireNotHalted`）。
3. 指示层的 8 秒空闲隐藏由全局 `_busy` 计数驱动，两个会话会互相推迟隐藏。

### 我卡在哪

**（a）会话身份怎么稳定拿到。** `desktop_diagnose` 里能拿到：

```
currentInitiator().id: session-3af2ac83-5562-4976-9f41-7d6d1259f130
```

但它是在 `diagnose` 的 execute 里调的，不是在 `authorize()` 里。要在
`grants` 上分键，得在每次授权/查询时都拿到会话 id。`ctx.get('agents')`
返回的对象的完整接口我没看过，只知道有 `currentInitiator()`。

**（b）会话结束时怎么清理。** 把 `grants` 改成 `Map<sessionId, Set<base>>`
之后，会话结束不会自动清空，会一直堆着。`workspaceRegistry.list()` 返回
的 `sessionIds` 是历史累计的（本机 18 个），不能用来判断谁还活着。
所以问题是：**插件有没有办法知道"某个会话结束了"**？还是只能靠 TTL？

**（c）闸门该不该按会话分。** 这是我真正没想清楚的地方：

- 用户按 ESC 时，他看到的是屏幕上有东西在动，**他不知道是哪个会话**。
  所以直觉上闸门应该**全局**拉下 —— 那"会话隔离"的这一半就不做了？
- 但如果全局拉下，会话 A 被自己的急停连累了会话 B，这合理吗？
- 另一种可能是：闸门全局，但**只有发起者能解除**。

**我没有判断依据，想问的是：在这种"一个用户、多个 agent 会话共用一台机器"
的模型下，急停的合理语义是什么？**

**（d）`grants` 的值现在存的是字符串 `'session'`。** 如果改成按会话分，
这个值该存什么、`effectiveAllowlist()`（`toolset.mjs:95`）怎么合成，
我看得出来要改，但不确定有没有更简单的结构。

### 我试过什么

只做了核查，没动手。确认了 `index.mjs` 没有自己维护第二份 grants
（我一开始以为有，是错的）。

## 二、输入串行化：`_busy` 是计数，不是锁

### 现状

`plugin/index.mjs:580`：

```js
let _busy = 0
// register() 的包装里：
_busy++
try { ... } finally { _busy-- }
// 另一处：
if (_busy > 0) return   // 指示层空闲隐藏的判断
```

它唯一的用途是**让指示层不要在操作进行到一半时消失**（否则 ESC 监听窗口
会关掉，用户按 ESC 就没人接了）。

### 后果

两个会话同时操作时，没有任何互斥。具体会坏成这样：

```
会话A: 截图 → 算出 Alpha 按钮在 (186,161)
会话B: 把窗口拖走了
会话A: 点击 (186,161)          ← 点到别的东西
```

`shotId` 能防住"窗口移动后还用旧坐标"（`plugin/index.mjs` 的 `checkShot`
会拒绝），但它防不住**会话 B 在 A 的截图之后、点击之前**动了界面 —— 因为
那时窗口确实没移，是内容变了。

### 我卡在哪

**（a）范围。** 如果插件是单例，一个进程内只需要一个**内存锁**就够了。
但用户可能开**两个 DSH 进程**，那就是跨进程竞争 —— 那种情况要不要管？
如果要管，是文件锁还是命名互斥体（`CreateMutex` + `Local\` 或 `Global\`）？

**（b）锁的粒度。** 一次操作要锁多久？

- 只锁 helper 那一次调用（约 110ms）？那"截图→算坐标→点击"这个序列里，
  截图和点击之间的空隙仍然敞着。
- 还是整个工具调用（含截图）？那 `observeAfter` 里再截一次图算不算？
- 还是"观察 + 后续动作"绑成一个事务？那需要引入 observation 令牌，
  又回到报告说的"统一观察对象"，是更大的改动。

**（c）等锁的时候做什么。** 立刻失败并告诉调用方"别的人在操作"，
还是阻塞等待？阻塞的话超时多长？

### 我试过什么

没有。我只确认了 `_busy` 不是锁。

## 三、错误分类：helper 有 15 种错误码，但没有"该怎么恢复"

### 现状

`helper/src/Program.cs` 里 29 处 `FailJson("SomeCode", ...)`，去重后：

```
ActionNotAvailable AmbiguousTarget BadAction BadIndex BadValue Halted NotFound
NotSettable OutOfRange PatternLost RangeUnavailable ReadOnly Refused
StaleSnapshot UiaError
```

`toolset.mjs` 的 `failMessage(r)` 把它们转成**中文句子**给模型看。

### 问题

报告要求的是结构化恢复建议，例如：

```
{ code: 'StaleTarget',    retry: 'reobserve' }
{ code: 'TargetOccluded', retry: 'wait' }
{ code: 'AmbiguousTarget',retry: 'disambiguate' }
```

而现在是"失败：目标窗口 12345 不存在或已关闭。先用 desktop_list_windows 重新确认。"
—— 一句话，让读的人自己判断。

### 我卡在哪

**（a）helper 判不出来。** 有些错误在 helper 层是一码事，对调用方是另一回事：

- `NotFound` 可能是窗口关了，也可能是元素还没渲染（该等），也可能是
  描述符写错了（该改）。
- `Refused` 有多种来源：白名单、坐标不在目标窗口、闸门。它们的恢复动作
  完全不同。

**helper 不知道自己为什么被调用**，所以它判不出来"该重观察还是该等"。

**（b）那这个判断该放在哪？** 我的想法是在 `toolset.mjs` 的
`failMessage()` 里，按 `code` + 上下文映射成 `retry`。但那样要改 29 个
失败点的上下文传递 —— 每个 `FailJson` 得带上"我是在哪个阶段失败的"。

**想问的是：有没有更省的做法？** 比如只给少数"高频且恢复动作明确"的
错误加 `retry`，其余保持文字。

**（c）`retry` 该是给模型看的，还是给调用代码看的？** 如果给模型看，
它就是一个字符串字段，模型读到后自己决定 —— 那和现在的中文句子差别不大。
除非 DSH 的工具有某种"结构化错误 + 自动重试"的机制。**我不确定 DSH
对工具错误的约定是什么**，这可能需要看 `dsh-tools` 的文档。

## 四、分段计时：不知道该埋在哪一层

### 现状

helper 里**没有**任何计时（`performance.now` / `Date.now` 出现 0 次）。
`toolset.mjs` 有 1 处，`index.mjs` 有 6 处（都是 shotId 时间戳、空闲计时）。

我知道的数字只有手工测的两次：

```
helper 往返约 110 ms
模型一轮约 40 s（比值约 1:360）
```

### 我卡在哪

**（a）一次工具调用其实有多段。** 以 `desktop_click` 为例：

```
checkShot（纯内存）
→ toolset.click
    → list_windows（另起一个 helper 进程）
    → click（又一个 helper 进程）
→ observeAfter
    → sleep(settleMs = 220)
    → screenshot（第三个 helper 进程）
```

所以"一次点击"里有 **2~3 个 helper 进程**、一个固定 sleep、加截图。
不知道时间怎么分。

**（b）埋在哪。** 三个选项，我都不满意：

- helper 里：只能测到自己那一段，测不到进程启动的固定开销（那恰恰是最贵的）。
- toolset 里：能测到每次 `runHelper`，但要改 20 多处调用点。
- 外层包一层：能测到总时间，但分不出段。

**（c）测出来给谁看。** 这个我完全没想清楚：

- 给模型看 → 每轮都要读这些数字，消耗 token，而且模型也不太会用它做决策。
- 给开发者看 → 写日志文件，但 DSH 插件的日志在哪、怎么查，我不知道。
- 或者只在 `desktop_diagnose` 里暴露最近 N 次的耗时？

**想问的是：这种"想知道慢在哪"的需求，在 DSH 插件里通常怎么满足？**

## 五、一个附带的疑问（可能比上面都重要）

`shotId` 的契约现在是这样：

- `desktop_screenshot` 返回 `shotId` + 坐标几何
- `desktop_click` / `drag` / `move` 接受 `shotId`，校验窗口没移、没改大小、没过期
- `wheel` / `drag` / `type` 执行后作废该窗口所有 shotId

但这个契约有一个漏洞我没堵上：**`scroll` 之后内容变了，而 `shotId` 只检查
窗口几何**。我加了"滚轮后作废"，但如果**别的进程/用户**滚动了呢？那
`shotId` 仍然有效，坐标却已经不对。

**想问的是：有没有办法让"这张截图是否还代表当前画面"变得可验证？**
我能想到的都是像素比对（贵、且要求截图可复现），或者 DWM 的某种变更通知。
