# 定案：注入能力取决于启动上下文，与代码无关

**日期**：2026-10-14
**结论**：同一份二进制 `InjectSelfTest.exe`

| 启动方 | 起始光标 | SetCursorPos ×3 | SendInput 相对 | 结果 |
|---|---|---|---|---|
| Codex 的 shell | **(0,0)** | 全部 `ret=False` | `ret=0`，位移 0 | **0/3** |
| Codex 的 computer use helper（`launch_app`） | **(1574,1123)** | 全部 `ret=True`，精确命中 | `ret=1`，位移 (60,60) | **3/3** |
| 我的 shell（DSH 子进程） | (1059,1143) | 全部 `ret=False` | `ret=1`，位移 (0,0) | **0/3** |

**代码一行没改。唯一的变量是"谁启动它"。**

## 这推翻了本项目此前所有的归因

追查这一天的过程中，我给过很多解释，**全部是错的**：

| 我曾归因于 | 实际 |
|---|---|
| 我把鼠标代码改坏了（`SetCursorPos` vs `SendInput`） | ❌ 代码是对的 |

| 完整性级别 / 提权 | ❌ 双方都是 ElevationType=3 |

| `BlockInput` | ❌ 解除后仍无效 |

| 合成前台切换导致输入被压制 | ❌ 是表象之一，不是根因 |
| 读 `SetCursorPos` 的 last-error | ✅ **这条是真错**（该 API 不设置 last-error） |
| 用返回值当判据 | ✅ **这条是真错**（应读光标实际位置） |

**最后两条是我真正的错误，但它们是"测量方法的错误"，不是"根因"。**

## 已知的事实

**能注入的上下文**：Codex 的 computer use helper（`codex-computer-use.exe`）
**不能注入的上下文**：任何 shell 进程（Codex 的、我的都是）

Codex 自己的解释：

> Computer Use 能真的移动鼠标，是因为它的 helper（`codex-computer-use.exe`）
> 是**独立进程，不在我这个 shell 的沙箱里**。

**关键旁证**：不能注入的那些 shell，光标读数是 `(0,0)` 或读得到真实值——
两种都有，**但都不能注入**。所以"能读到光标"不等于"能注入"。

## 补充对照：两个候选变量都被排除（2026-10-14）

用户提出一个更精确的观察：**凡是经过 shell 的启动链都失败，不经 shell 的直接启动成功**，
建议测试"绕开 shell 中间层"。

### 对照 1：绕开 shell 中间层 —— 仍失败

**我的插件本身就是直接从 DSH 宿主进程 `spawn` `dsc.exe` 的**
（Node 的 `spawn`，中间没有 bash / powershell）。
之前我一直用 bash 手动调 `dsc.exe`，那才是走 shell 链的路径。

直接调用插件工具（`desktop_click` → DSH 宿主 `spawn` `dsc.exe` → `SetCursorPos`）：

```
结果: SetCursorPos(1700,600) 失败 (Win32 错误 0)
```

**即"无 shell 中间层"这条路径同样失败。** 假设被推翻。

### 对照 2：进程存活时间 —— 无关

Codex 的 helper 是**常驻进程**，我的 helper 是**一次性进程**。
测"进程存活多久才可能可注入"（`tools/diag/InjTiming.cs`，6 轮 × 2 秒间隔）：

### 对照 3：用 explorer 转发启动 —— 做不了

用户尝试用 `explorer.exe` 转发启动（模拟双击），失败：
**agent 的 shell 调不动用户所在会话里的 explorer**，没有新窗口出现，日志也没被改写。
所以"用户双击"这条路**必须由用户自己点**，agent 代劳不了。

### 现在剩下的唯一变量

已经排除：**shell 中间层**（对照 1）、**进程存活时间**（对照 2）、
**令牌特征**（AppContainer / 提权 / 会话 / 窗口站 / 桌面 / 作业限制全部正常）。

**剩下的是 DSH 自己的启动上下文** —— 所有 DSH 的后代进程都继承它。

**最便宜的验证**：**从普通的命令提示符或快捷方式重启 DSH**
（不要从任何 agent 会话启动），再跑一次 `InjectSelfTest`。

- **3/3** → 问题彻底解决，且使用条件明确：不要从 agent 会话启动
- **0/3** → 限制更根本，与启动方无关，需要换完全不同的思路

**这一步比继续推理便宜得多，而且是唯一能把"DSH 的启动上下文"这个变量单独摘出来的办法。**

## 最终定案：限制在「我的进程」上，不在目标窗口上（2026-10-14 16:30）

### 三组外部对照（用户与 Codex 提供）

| 谁启动的进程 | 结果 |
|---|---|
| Codex 的 computer use helper（`launch_app`） | **3/3**，精确命中 |
| **explorer.exe 双击**（用户鼠标操作，父进程 = explorer，全程无 agent shell） | **3/3**，精确命中 |
| agent 的沙箱 shell 派生 | **0/3**，且光标读成 `(0,0)` |

**坏掉的既不是机器、也不是鼠标 API，而是"agent 沙箱 shell 里生出来的进程"这个特定上下文。**

### 决定性的一测：干净目标窗口 + 我的 helper → 仍失败

用户双击 `DoubleTarget.exe`（父进程 = explorer），它启动了一个记事本子进程——
**两者都在干净上下文里**。我用 helper 点那个记事本，条件全部满足：

```
前台窗口   = 395156 [Notepad]           ← 目标确实在前台
命中校验   = root=395156 notepad.exe    ← 白名单通过
SetCursorPos(1559,498) → 失败
光标       = 停在起始位置，没有移动
```

**目标干净、目标在前台、校验通过——我的进程依然注入不进去。**

### 所以

```
不是目标窗口的问题  →  是「我的进程」的问题
```

**我的 helper 处在受限上下文里，无法向任何外部窗口注入。**
它能注入的只有它自己那个上下文里创建的东西（我的 WinForms 测试窗口）。

### 唯一剩下的解决办法

**从干净上下文启动 DSH** —— 也就是**双击桌面图标或从开始菜单启动**，
不要让它成为任何 agent 会话的后代。

预期：那样启动后，helper 的注入能力应当和 explorer 双击的进程一样（3/3）。

**这是唯一剩下的路，而且已经有了强旁证**（explorer 这条用户路径是干净的）。
