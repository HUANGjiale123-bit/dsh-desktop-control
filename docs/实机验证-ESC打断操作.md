# 实机验证：ESC 打断正在进行的操作

**日期**：2026-10-15
**结论**：通过。每一环都有独立证据。

---

## 这是"演示"，不是"自测"

之前的验证都是我调工具、读返回值。**这一次不一样**：

- 助手**真的在连续操作**记事本（打字）
- **人**在中间按物理 ESC
- 判据是**下一次操作被拒绝**，不是"我按了停止键"

**为什么这个区别重要**：没有真在干活的时候，"停止"是看不出来的。
助手如果只是"在等待"，看起来也像"被停住了"——**这是我之前在演示里踩的坑**，
用户按 ESC 时我以为生效了，其实我只是在 sleep。

---

## 实验过程与证据

### 前置

```
闸门          已解除（halted=false）
记事本        hwnd=1050420，确认在前台（foreground=1050420）
指示层        desktop_indicate → 光带 + 逃生条
```

**"确认记事本在前台"这一步不能省。** 上一次演示失败就是因为焦点被 DSH 抢回去了，
而 `desktop_type` 照样报"已输入"——字进了别的窗口。**报告的是"调用了"，不是"到了"。**

### 操作序列

```
点击记事本       → 已在 (1500,600) 执行 left 键点击
打字【1】        → 已输入 15 个字符          ✅
打字【2】        → 已输入 18 个字符          ✅
打字【3】        → 已被急停：闸门文件存在，拒绝执行 type   ← 人按了 ESC
```

### 证据链

| 环节 | 证据 |
|---|---|
| **钩子抓到物理按键** | 日志 `[16090ms] 真实按键 vk=0x1B  <= ESC` |
| **闸门写入成功** | 日志 `[16094ms] 闸门已写入: D:\dsh workspace\.desktop-control\halt` |
| **闸门确实存在** | 文件时间戳 `2026-10-15 14:25:21` |
| **界面退出** | `dsc-esc` / `dsc-edge` 进程列表为空 |
| **操作被拦住** | 第 3 次打字报 `已被急停` |
| **前两段真的写进去了** | 记事本标题 `*代码.txt` —— `*` 是记事本的修改标记 |

**最后那一行是必要的**：它证明"前两次成功"是真的成功（内容进了文档），
而不是"两次都失败了、第三次只是第一次失败"。没有它，
"第三次被拒"这个结果可以有别的解释。

### 日志里的一个细节

```
[15022ms] 心跳：入口 30 次，真实按键 0 次
[16090ms] 真实按键 vk=0x1B  <= ESC
```

**心跳那一行说明钩子在正常工作**：入口 30 次 = 它看到了 30 次按键消息，
其中"真实按键 0 次"是因为助手注入的按键带 `LLKHF_INJECTED` 标志、被正确排除。

**这个区分很重要**——否则"钩子收到了注入按键"会被误读成"用户在按键"。

## 这一轮暴露并修掉的问题

### 问题一：界面停了，控制没停（用户发现）

> **我按 esc 指示层消失不见了，但你照样能操控。**

`dsc-esc` 退出 → 光带和逃生条消失 → **但闸门没写成** → `dsc.exe` 照常执行。

**根因**：`dsc-esc` 的日志路径是第二个参数，而插件**从来不传**，
于是 `L()` 直接 `return`，整个程序静默运行。写闸门失败时一片空白。

**修法两条**：

1. **日志路径从闸门路径自动推导** —— 不依赖调用方记得传参
2. **写闸门失败时不退出** —— 界面留在屏幕上就是"还没停成"的信号；
   写失败还照样退出，等于骗用户

### 问题二：`dsc-edge` 的钩子确实不触发

单独起 `dsc-edge --escape`（带逃生条），按 ESC 后**闸门未生成**。
它的逃生条是靠"关窗口"路径退出的，**那不等于停止**。

所以"只留 dsc-edge"不可行；要精简只能保留 `dsc-esc` 并把光带并入它。

## 可复现的操作步骤

```bash
# 1. 清闸门（否则第一次操作就被拒）
DSC_HALT_GATE="D:\dsh workspace\.desktop-control\halt" \
  helper/bin/dsc.exe stop --clear

# 2. 确认目标窗口在前台（不能省）
#    desktop_list_windows 看 foreground 字段

# 3. 开状态
#    desktop_indicate

# 4. 连续操作 → 人按 ESC → 下一次操作应报"已被急停"

# 5. 验证
cat "/d/dsh workspace/.desktop-control/esc.log"   # 应有 vk=0x1B
cat "/d/dsh workspace/.desktop-control/halt"      # 应有时间戳
```

**注意第 1 步用 `DSC_HALT_GATE`**：直接跑 `dsc.exe` 时它按自身位置推默认路径，
你看到的"没拦住"可能是路径不对，而不是闸门没生效——**这个假阴性我踩过**。

## 第二次实机验证：操作真实第三方应用 + 指示层自动出现（2026-10-15 晚）

这一轮验证的是**上一轮修掉的那个缺口**，所以比第一次更有意义：
第一次的指示层是手动开的，这次全程没调 `desktop_indicate`。

### 做了什么

```
① 启动腾讯视频（D:\QQLive\QQLive.exe）→ 3 个进程，没闪退
② 读无障碍树，找到搜索输入框：Edit @(676,43 170x34) [value:settable]
③ desktop_set_value 写入"一拳超人" → 回读确认 "" → "一拳超人"
④ 此时**指示层自动出现**（我没调 desktop_indicate）
⑤ desktop_press_key Enter 提交
⑥ 结果页正确加载：一拳超人 / 第三季 / 第二季，每条都有"外站播放""想看"
⑦ 用户按物理 ESC
```

### ⑦ 之后的完整证据链

```
[21189ms] 真实按键 vk=0x1B  <= ESC
[21190ms] 钩子捕获 ESC（入口累计 3 次）
[21196ms] 闸门已写入: D:\dsh workspace\.desktop-control\halt
闸门:      ✅ 15:04:29 生成
指示层:    ✅ 进程退出 → 光带 + 逃生条一起消失
后续操作:  ✅ "已被急停" —— 真的被拦住了
```

### 为什么"指示层自动出现"是关键

**上一轮暴露的缺口**：助手忘了调 `desktop_indicate`，于是好几轮真实操控是在
**屏幕上毫无提示**的情况下进行的。用户指出"你操作腾讯视频不就是 computer use 吗"。

**修法**：把提示绑到授权路径上（`onAuthorized` 钩子）——
放行之后、执行之前自动确保指示层在跑。

**这次验证的正是那一点**：我只写了个搜索框，提示就自己出现了。

### 两个观察（未解决，如实记录）

**① 授权询问没有出现。** 重启后会话授权本应清空，但操作没有弹询问。
需要查清是"授权意外存活"还是"批准过程太快没显示"。**这一条关系到安全模型是否真的生效。**

**② `desktop_click` 用无障碍树给的坐标点了两次都没反应**，而按回车立刻生效。

```
树里报的:  Button @(870,45 30x30)
换算桌面坐标: (350+870+15, 14+45+15) = (1235,74)
点了两次:  截图完全没有变化
```

**Electron 应用的 UIA 矩形不够可靠，不能拿它当点击依据。**
这也解释了为什么这个流程能成——靠的是 `desktop_set_value`（走无障碍接口，不用坐标）
加回车。**坐标点击对这类应用应当视为不可靠路径。**
