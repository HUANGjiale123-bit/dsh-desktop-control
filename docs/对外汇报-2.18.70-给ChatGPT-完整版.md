## 1. 项目是什么

一个 **DSH/Cordis 插件**，让 Windows 上的 agent 能看屏幕、操作界面：

| 能力组 | 工具 | 说明 |
|---|---|---|
| 应用与窗口 | `list_apps` `launch_app` `list_windows` | 应用清单来自注册表；启动后核实窗口出现 |
| 观察 | `read_window` `screenshot` `visual_candidates` `visual_view` | 无障碍树优先；读不到时走截图 + 本地 OCR |
| 输入 | `click` `click_element` `click_candidate` `type` `press_key` `set_value` `move` `drag` `hold` `release` `wheel` `do_action` | 注入前校验前台、完整性、落点归属 |
| 辅助 | `whatis` `indicate` `resume` `off` `revoke_grants` `diagnose` | 权限、急停、诊断 |
| 光标装饰（默认关） | 无独立工具，由配置开启 | 把系统光标换成画出来的鲸鱼女仆 |

**架构**：插件（Node）→ `dsc.exe` helper（C#）→ Win32/UIA；光标装饰是独立的 `dsc-fx.exe` + 看门狗 `dsc-guard.exe`。

**安全模型**（这是它区别于手写 AutoHotkey 脚本的地方）：

- 静态白名单 + 会话级授权，按 **exe** 授权，不按窗口
- 写入类操作前确认前台、完整性级别、落点归属；**拒绝比点错好**
- ESC 急停：写闸门文件，此后所有操作被拒；`desktop_resume` 显式恢复
- 看门狗：装饰进程被强杀时恢复系统光标（实测 429–470ms）

## 3. 四个真问题

### 3.1 A：弹出菜单点不了

**现象**：打开记事本「编辑」菜单，点「时间/日期」被拒绝：

```
Refused — 坐标 (648,536) 现在属于窗口 2493216（notepad.exe），不是指定的目标窗口 1378614
```

**根因**（比报告推测的更深一层）：点击流程**先激活目标窗口**：

```
RequireActivated(主窗口)   ← 激活的瞬间，弹出菜单被关掉
WindowFromPoint            ← 此时该坐标已回到文档区
root != target → 拒绝
```

激活动作本身就把要找的东西弄没了。

**修法**：先解析落点属于哪个进程，再决定：

- 同进程、不同窗口（典型就是菜单/下拉/工具提示）→ **按同一应用对待，且不激活**
- 其它情况 → 保持原行为：拒绝，绝不替用户去点遮挡者

**证据**（`test-menu-click.mjs`，真实 WinForms 菜单 + 真实鼠标注入）：

```
✓ 菜单栏点击被接受
✓ 菜单已打开，菜单项在 (511,390)
✓ 点击被接受（没有被"不是指定的目标窗口"拒绝）
✓ 落点是同进程的另一个窗口（10881370）—— 弹出菜单的预期行为
✓ 菜单项的 Click 事件执行了（日志有记录）
```

第三方在真实记事本上复验：菜单项写入时间戳，标题变为 `无标题 - 记事本 *`。

**没覆盖**：跨进程弹出菜单（如某些托盘菜单）仍被拒绝，这是有意保留的保守行为。

### 3.2 B：完整性级别——我的解释是错的

**原判断**：同一份二进制报不同级别，"合理解释是父进程不同"。

**第三方的对照实验**：同一次 pwsh 调用、**同一父进程（Medium）**、三份**哈希相同**的 exe：

| 位置 | 自报 |
|---|---|
| profile | Medium |
| 工作区内 | **Low** |
| `%TEMP%` | Medium |

父进程这个变量被彻底排除。

**真实机制**（它用 `icacls` 验证）：

```
icacls <工作区>          → Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)
icacls <工作区>\dsc.exe   → Mandatory Label\Low Mandatory Level:(I)(NW)   ← 继承
icacls %TEMP%\dsc.exe    → （无标签）
```

DSH 的 ACL 沙箱把工作区目录标成 Low，文件**继承**标签；带 Low 标签的可执行文件启动后，
进程就是 Low 完整性。

**修法**（采纳它的建议）：`ping` 同时报告**令牌级别**与**文件自身的强制标签**，实现是读
安全描述符里的 `SYSTEM_MANDATORY_LABEL_ACE`，不是按路径猜：

```
工作区副本 → 令牌: Low | 文件标签: Low(4096)
%TEMP% 副本 → 令牌: Medium | 文件标签: 未知
```

第三方复验：在受限沙箱里连令牌都读成"未知"，而**文件标签仍稳定可读**——这个字段比原设计更有用。

### 3.3 C：卸载后残留孤儿进程

**现象**：卸载后 `dsc-fx.exe` 与 `dsc-guard.exe` 残留，要手动停；顺序错了还会互相拉起。

**根因**：

1. 插件每次桌面操作都 `start()`，它只要还活着就会把停掉的那个**重新拉起**
2. `guard` 只在收到 `fx.stop` 时退出；插件卸载时没人写，它就永远挂着

**第一版修法**：插件 `setInterval` 每 5 秒写 `fx.heartbeat`，插件消失 → 心跳停 → 子进程自退。

**第三方的判别实验**（这一轮最关键的一次）：

```
杀完 20:33:32   fx=无 guard=无
20:33:38   heartbeat=20:33:37
20:33:45   heartbeat=20:33:42
（持续 7 分钟）
```

两个装饰进程都死了，心跳还在刷新 → 写入者是**宿主里残留的定时器**。
HMR 卸载不走 `dispose`，`clearInterval` 从未执行。

**第二版修法**：**删掉定时器**。心跳只在真实工具调用时写。"不再被使用"就等于"心跳过期"：

- `dsc-fx` 25 秒内恢复光标并退出
- `dsc-guard` 同一判据，恢复并退出
- 下次操作重新拉起（实测 <2 秒）

**证据**（`test-cursor-idle-exit.mjs`，测的正是上一版漏掉的那半）：

```
✓ 心跳已写入
✓ 心跳没有被后台定时器继续刷新     ← 上一版会在这里失败
✓ dsc-fx 在无操作后自行退出（24 秒）
✓ dsc-guard 也已退出
✓ 再次调用后 dsc-fx 重新启动
```

第三方重启 DSH 后实测：心跳年龄单调增长，两个进程在 **22~26 秒**消失，`fx.blanked` 同步清除。

### 3.4 D：验证方法本身的漏洞

上一轮我把"修复"写进汇报时，验证的是**"心跳断了会退"**，从没验证**"心跳到底会不会断"**。

这是这一轮最重要的教训，已写进验收规范：

> 验证修复要覆盖**触发条件本身**，而不只是修复后的行为。

不是"几个 bug"，而是**四类会反复出现的错误**：

| 类型 | 实例 | 后果 |

## 5. 机制化改进（不靠记性）

### 5.1 文档审计接进提交钩子

`tools/audit-docs.mjs` 从**代码本身**取事实比对文档：

- 工具名必须真注册过；helper 子命令必须真在 `case` 里

- 引用的路径必须存在
- **`dist/` 副本必须与源文件逐字节一致**（这条直接抓出了旧清单）

不一致 → 提交被拦下。当前 7 个文档通过。

### 5.2 新增回归测试

| 测试 | 钉住什么 |
|---|---|
| `test-menu-click.mjs` | 真实菜单 + 真实点击，验证菜单项**真的执行**（副作用，不是返回码） |
| `test-cursor-orphan.mjs` | 不发停止信号、只停心跳，两个进程必须自退并恢复光标 |
| `test-cursor-idle-exit.mjs` | **插件活着但不活动**时也必须自退 |

### 5.3 进程归属

测试曾按**进程名**判断生死，结果被机器上真实安装的插件干扰（本机残留了四个 `dsc-fx`/`dsc-guard`）。
现在按**命令行里的 watch 目录**识别"自己起的进程"，既不误判也不误杀。

## 7. 安装 / 升级 / 卸载

### 安装（手动，三步，一步都不能少）

```powershell
cd C:\Users\<你>\.dsh\profiles\desktop
copy package.json package.json.bak
pnpm add file:C:/path/to/dsh-desktop-control-2.18.70.tgz
# 手动把 "dsh-desktop-control" 加进 package.json 的 dsh.profile.bundles
node -e "JSON.parse(require('fs').readFileSync('package.json','utf8')); console.log('OK')"
```

**不要手改 `cordis.patch.yml`**——早期版本在这里写错过。

### 升级

**必须重启 DSH**。带定时器的旧版本在 HMR 升级时不会被 dispose，旧定时器会继续喂心跳，
让新的自退机制看起来完全失效。

### 卸载

1. 先从 `dsh.profile.bundles` 移除 `"dsh-desktop-control"`
2. 再 `pnpm remove dsh-desktop-control`
3. 重启 DSH
4. 删掉 `package.json.bak`（它记的是"装到一半"的状态）
5. 等 25 秒：两个装饰进程会自己退出并恢复光标；想立刻收可 `taskkill`，**顺序无所谓**

顺序反了会留下悬空 bundle 引用，DSH 可能起不来——第三方实测过。

## 8. 已知限制（完整清单）

| 限制 | 状态 | 说明 |
|---|---|---|
| 跨进程弹出菜单 | 不支持 | 维持"拒绝而不是乱点" |
| `click_element` 对不可激活窗口 | 未改 | 坐标点击已覆盖菜单场景 |
| 多显示器 / 100% 缩放 | **未验证** | 开发机单屏 150%；第三方 125%；三处缩放只覆盖了 125/150 |
| 长稳 30 分钟 | **未做**（按用户要求） | 3 分钟采样 CPU 0.14%，不能据此断言无泄漏 |
| 卸载路径的独立触发验证 | 未严格完成 | 第三方在 25 秒内没来得及完成卸载；已论证与空闲自退共用判据 |
| 指示灯 `_idleTimer` | 已知风险 | 无 dispose 时也会留在宿主里；影响仅"多空转几次" |
| 应用私有光标 | 有兜底 | `fx.log` 出现 `yield(不认识的光标)` 时让位显示系统光标，属预期 |
| 截图排除 | **未处理降级** | 装饰层用 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` 排除在截图外，但**代码没有检查返回值**，也没有按系统版本降级。低于 Windows 10 2004 时装饰可能出现在截图里——这一点没有验证过，也没有兜底 |
| 完整性 | 需 Medium | 从 Low 令牌运行会让注入静默失效；`ping` 现在会报文件标签帮助定位 |

## 10. 请评审重点看的五个问题

1. **"同进程窗口 = 同一应用"** 的放宽是否合适？授权按 exe 给，但一个进程可以用弹出窗口
   诱导点击它自己的其它窗口。有没有更细的判据（例如只放行 owner/WS_POPUP）？
2. **心跳方案的边界**：假设"插件不再被使用 = 心跳过期"。用户开着插件长时间不动时，
   子进程会退出、下次操作重新拉起（实测 <2 秒）。这个取舍可接受吗？
3. **文件标签字段**（`exeFileIntegrity`）在受限环境里比令牌更稳定，
   是否应作为排查"为什么注入失效"的首选指标？
4. **卸载自退的独立验证**：有没有比"脚本内触发→卸载→计时"更简单的办法？
5. **公开仓库的风险**：这个插件能注入鼠标键盘、读屏、绕过部分前台限制。
   有没有需要在上架前补的**滥用防护**（例如默认关闭、首次启用二次确认、日志留痕）？
