# 对外汇报 v2.18.70：第三方验收的四轮交锋

> 这份报告只写**事实、错误的判断、以及被推翻的过程**。
> 四份第三方报告（2.18.65 验收 → 2.18.66 复核 → 2.18.68 验收 → 2.18.69 验收）
> 全部保留在仓库 `docs/` 下，本文是对它们的回应总结。

---

## 0. 一句话

这一轮的价值不在"实现了一个功能"，而在**第三方用对照实验和副作用验证，连续推翻了我三个
"看起来合理"的判断**：菜单点不了的根因、完整性级别的解释、以及卸载自退的验证方法。
每一条都补了回归测试，并把能机械检查的部分做成了提交门禁。

## 1. 第三方抓到的四个真问题

| 版本 | 问题 | 根因 | 我的原判断 |
|---|---|---|---|
| 2.18.65 | **Win32 弹出菜单项点不了** | 点击流程**先激活目标窗口**，激活会关掉弹出菜单，随后拿一个已消失的菜单坐标去比对 | 报告说"落点校验按 HWND 判定"，对了一半 |
| 2.18.68 | **卸载后残留 fx/guard 孤儿进程** | 插件每次操作 `start()` 会拉起已停的子进程；guard 只在收到 `fx.stop` 时退出 | 没意识到卸载会留孤儿 |
| 2.18.68 | **完整性级别"按路径推断"** | DSH 把工作区目录标成 Low，文件继承标签，带标签的 exe 启动后进程就是 Low | 我解释成"父进程不同" ❌ |
| 2.18.69 | **自退机制永不触发** | HMR 卸载不走 `dispose`，`setInterval` 留在宿主里继续写心跳 | 我验证了"心跳断了会退"，没验证"心跳会不会断" ❌ |

### 1.1 菜单：修复与验证

修法：先解析落点属于哪个进程，**同进程的另一个窗口**按同一应用对待，且**不激活**
（激活正是关菜单的动作）。

验证用的是**副作用**而不是"没报错"：

```
✓ 菜单栏点击被接受
✓ 菜单已打开，菜单项在 (511,390)
✓ 点击被接受（没有被"不是指定的目标窗口"拒绝）
✓ 落点是同进程的另一个窗口 —— 弹出菜单的预期行为
✓ 菜单项的 Click 事件执行了（日志有记录）
```

第三方在记事本上复验：菜单项真的写入了时间戳，标题变成 `无标题 - 记事本 *`。

### 1.2 完整性：我错了，它对了

它的三位置对照（**同一次调用、同父进程、三份哈希相同的 exe**）：

| 位置 | 自报 |
|---|---|
| profile | Medium |
| 工作区内 | **Low** |
| `%TEMP%` | Medium |

这把"父进程"这个变量彻底排除。真实机制是文件标签继承。

采纳它的建议后，`ping` 现在同时报**令牌级别**和**文件标签**：

```
工作区副本 → 令牌: Low | 文件标签: Low 4096
TEMP 副本 → 令牌: Medium | 文件标签: 未知
```

它后来还发现：在受限沙箱里连令牌都读成"未知"，而**文件标签仍然稳定可读**——
这个字段比我原以为的更有用。

### 1.3 卸载自退：第一次修错了对象

第一版：`setInterval` 每 5 秒写心跳，设想"插件卸载后心跳停止 → 子进程自退"。

第三方杀掉两个进程后观察到**心跳仍在刷新**，持续 7 分钟：

```
杀手 20:33:32   fx=无 guard=无
20:33:38   heartbeat=20:33:37
20:33:45   heartbeat=20:33:42
```

→ 写入者是**宿主里残留的定时器**（HMR 不 dispose 旧实例）。

第二版：**删掉定时器**，心跳只在真实工具调用时写。"不再被使用"就等于"心跳过期"。
验证也补上了缺失的那半：

```
✓ 心跳没有被后台定时器继续刷新     ← 上一版会在这里失败
✓ dsc-fx 在无操作后自行退出（24 秒）
✓ dsc-guard 也已退出
✓ 再次调用后 dsc-fx 重新启动
```

第三方重启 DSH 后实测：心跳年龄单调增长，两个进程在 **22~26 秒**之间消失，`fx.blanked` 同步清除。

## 2. 我犯的错误，按性质分类

这一轮暴露的不是一个 bug，而是**四类反复出现的错误**：

| 类型 | 实例 | 后果 |
|---|---|---|
| **靠"看起来合理"下结论** | 完整性级别归因于父进程 | 第三方要做一次对照实验才能推翻 |
| **只验证了一半** | 验证"心跳断了会退"，没验证"心跳会不会断" | 修复完全无效，还多了个写盘泄漏 |
| **声称改了但没改** | 回应文档写"诊断日志附 mtime"，代码里没有（替换未匹配、静默失败） | 第三方逐字核对后发现 |
| **发错版本** | `dist/` 里的体检脚本和验收清单是旧副本 | 第三方说"和上一版字节相同" |

其中后两类是**交付流程**问题，已经用机制而不是记性解决（见 §3）。

## 3. 机制性改进（这一轮真正的沉淀）

### 3.1 文档审计（`tools/audit-docs.mjs`）

从**代码本身**取事实去比对文档，不一致就失败：

- 工具名必须真注册过；子命令必须真在 helper 的 case 里
- 配置键必须真被读取；版本号必须等于 `package.json`
- 引用的文件必须存在
- **`dist/` 副本必须与源文件一致**（这条直接抓出了那份旧清单）

它已接入提交钩子：文档与代码不一致时**提交被拦下**。

### 3.2 新增的回归测试

| 测试 | 钉住什么 |
|---|---|
| `test-menu-click.mjs` | 真实菜单 + 真实点击，验证菜单项**真的执行** |
| `test-cursor-orphan.mjs` | 不发停止信号、只停心跳，两个进程必须自退 |
| `test-cursor-idle-exit.mjs` | **插件活着但不活动**时也必须自退（上一版漏掉的判据） |
| `test-packaging-layout.mjs` | 素材是否都在 `files` 清单、发布 exe 是否被 git 跟踪 |
| `test-docs.mjs` | 文档审计接入快测 |

### 3.3 打包缺陷

fresh clone 后 `plugin/bin` 不存在（`.gitignore` 的 `*.exe` 把它一起忽略了），
打出来的包**一个可执行文件都没有**。已修，并加了"发布 exe 必须被 git 跟踪"的测试。

## 6. 想请评审看的四点

1. **"同进程窗口 = 同一应用"** 这条放宽是否合适？授权本来就是按 exe 给的，
   但现在一个进程可以用弹出窗口诱导点击它自己的其它窗口——有没有更细的判据？
2. **心跳方案的边界**：它假设"插件不再被使用 = 心跳过期"。如果用户开着插件长时间不动，
   子进程会退出、下次操作重新拉起（实测 <2 秒）。这个取舍是否可接受？
3. **文件标签字段**（`exeFileIntegrity`）在受限环境里比令牌更稳定，
   是否应该成为排查"为什么注入失效"的首选指标？
4. **卸载自退的独立验证**：有没有比"脚本内触发→卸载→计时"更简单的办法？

## 7. 一段自我评价

这一轮我最大的问题不是不会写代码，是**判断太快**：

- 看到"Low"就归因父进程，没做对照实验
- 验证修复时只测了会成立的那一半
- 文档里写了"已修"，但没回头看一眼代码

第三方的做法值得记住：**用对照实验否定假设，用副作用验证修复**。
这两条已经写进项目的验收规范（`docs/第二台机器验收清单.md` 开头）。
