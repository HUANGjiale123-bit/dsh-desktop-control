## 二、修了什么

| # | 问题 | 怎么发现的 | 验证方式 |
|---|---|---|---|
| 1 | 动作后返回的 shotId 立即被删 | Codex 探针 | **实机**：新 ID 点击成功 |
| 2 | 等锁超时泄漏 `_busy`、丢 trace | Codex 探针 | 静态（需真并发） |
| 3 | 排队期间取消仍派发点击 | Codex 探针 | **并发测试**（B 被取消后报取消） |
| 5 | hold 返回后锁释放、按键还按着 | Codex 探针 | 静态 + 行为测试 |
| 6 | Timeout 建议重放，可能重复副作用 | Codex 探针 | 静态 |
| 7 | 会话授权泄漏（全局 grants） | Codex 探针 | **实机**：本会话看不到别会话的授权 |

### 每个的根因，一句话

**① shotId 自杀**

`observeAfter` 登记新截图 → 外层 finally 按 hwnd **无差别作废** → 刚登记的也被删。

这是**「失效统一」和「动作后观察」两个功能的交界处** —— 单独看任何一个都是对的。

修复：`snapshotShotIds(hwnd)` 记下动作**前**的 ID，finally 只 `forgetShotIds(那些)`。

**② `_busy` 泄漏**

```
939:  _busy++
966:  等锁 → throw Busy     ← 在 try 之外
985:  try { ... } finally { _busy-- }   ← 所以不执行
```

后果：**空闲收起永久失效** + **失败 trace 丢失**（正好藏起竞争数据）。

修复：`_busy--` 和 `rememberTrace` 挪到**最外层 finally**；`releaseLease` 加 `leaseHeld` 守卫。

**③ 排队取消**

宿主在**派发工具前**查取消，但工具**已经进入、在插件内排队**时的取消没人管。

修复：`acquireLease(tool, signal)`，三个时间窗都查：
- 等待循环每轮
- 拿到锁后
- 派发动作前

**⑤ hold 所有权**

`hold` 结束而按键还按着，lease 却释放了 → 别的会话能插进来变成拖动。

修复：`pinLease()` 钉住，`desktop_release` 才放。
**而且 `desktop_release` 不再需要 lease** —— 一个恢复动作不该等它正要恢复的那把锁。

**⑥ Timeout 语义**

helper 超时 **≠ 动作没发生**。可能输入了一半、点了一下，超时发生在后续的 UIA 读取。

修复：`retry: 'wait'` → `retry: 'reobserve'`，并明说"动作可能已经发出"。

**⑦ 会话授权**

```
index 的 sessionGrants  → 只决定"要不要弹窗"
toolset 的全局 grants   → 决定"允不允许"
```

**而我们在弹窗里承诺的是「仅对当前会话有效」。** 承诺由 toolset 履行，而它不知道会话是谁。

修复：`grantsBySession: sessionKey -> Map`，sessionKey 来自 `exec.agent`。

**为什么用 `exec.agent` 而不是 `currentInitiator()`**：

> `currentInitiator()` 是**异步因果上下文**，不能作为永久存活证明。

一个是"这次调用属于谁"，另一个是"链路上最近一次是谁"。

## 三、三次被用户推翻的判断

这一节最重要 —— **这些不是 Codex 指出的，是我自己判错的**。

### 3.1 「用户发消息 = 继续任务」（当场推翻）

我让 `agent/inbox/inserted` 事件清掉急停闸门。理由是"用户想打断一下，说完就好"。

**用户原话**：

> 我说完话问题不一定是叫你继续任务啊？

**对。** 而且更讽刺的是：**对话本来就不受限**（只读工具从来没被闸门拦过），所以那个事件**没有任何东西需要解开**。

**一句话是不是"叫我继续"，是语义判断。** 它推不出来自"消息到达"这个事实。

### 3.2 「8 秒空闲收起是合理的取舍」（用户报"为什么退出两次"后才发现）

我在注释里亲手写了：

> 所以取 8 秒…代价是连续操作时会闪，但这本来就是无法避免的

**两处都错**：

| 我写的 | 实际 |
|---|---|
| "无法避免" | 该问的不是"停手后多快消失"，是"能不能跨过两步之间"—— 8 秒显然不能 |
| "代价" | 不是偶发代价，是**每一步都发生** |

**而模型一轮推理要 40 秒** —— 8 秒**必然**落在两次操作中间。

改成 90 秒。

### 3.3 「60 秒 TTL 够了」（Codex 指出后仍没改对）

Codex 说：

> 60 秒到期只证明时间过去了，不能证明旧任务停止。

我试图用"新消息"当任务边界 → 被 3.1 推翻。

**现在的答案**：**回到纯 TTL**，并且承认：

- 时间很笨，但它**不做语义判断**
- 真正的准确入口需要宿主提供**任务边界**（不是消息，是"这一轮结束了/新的一轮开始了"）
- 我没验证过 `agent/status`、`agent/assistant-stream` 的语义，**不敢用** —— 3.1 就是这么栽的

**补了一个显式工具** `desktop_resume`：用户明确说"继续"时，模型调它。

## 四、`resume → 操作 → off` 实测流程（2026-10-18 19:2x）

### 现场

```
用户：重启好了 试试开bilibili搜大肥鱼，当然我会按esc打断你
```

### 完整轨迹

```
① 启动 Edge              → hwnd=1444552
② Ctrl+L → 输入搜索 URL   → https://search.bilibili.com/all?keyword=大肥鱼
③ Enter                  → 搜索结果出来了

   （用户按 ESC，19:22:09，vk=0x1B）
   → 闸门写入

④ 我停了，**没有重试、没有自行解除**
⑤ 用户：「我又试着打断了下你，继续吧」
⑥ 调 desktop_resume({reason: "用户说「我又试着打断了下你，继续吧」"})
   → 已解除急停（依据：…）
⑦ 点击视频封面            → BV1GxpK6FE3o 播放页打开
⑧ 调 desktop_off         → 「已关闭 1 个指示浮层。闸门未拉下，无需处理。」
```

### 两次 ESC 的表现对比

**第一次**（真正的停止）：

```
Error: Halted — 已被急停：闸门文件存在，拒绝执行 click。
这不是故障，是用户按了 ESC 叫停。
**不要重试** —— 重试不会成功，只会让指示层反复冒出来。
也不要自行解除：急停是用户发起的，该由用户结束。
  [retry=stop]
```

**第二次**（收尾，不是停止）：

```
已关闭 1 个由本插件拉起的指示浮层与逃生条。 闸门未拉下，无需处理。
（这个工具只收界面，不改变急停状态。）
```

**"被停止"和"正常结束"是两件事，两段输出完全不混。**

## 五、两个值得记住的教训

### 5.1 一个反复出现的形状

**按人的节奏设的数，交给一个要想 40 秒的东西用。**

| 值 | 我按什么定的 | 实际使用者 |
|---|---|---|
| 8 秒 空闲收起 | 人的手速 | 每步思考 40 秒的模型 |
| 60 秒 急停 TTL | 人的耐心 | 同上 |
| "动作后观察" 的 shotId | 以为给人用 | 下一轮模型要靠它 |

**用户连着报了三个问题，根子都在这里。**

### 5.2 静态检查抓不到的

这轮有两个 bug **静态完全正常**：

**`desktop_resume` 永远拒绝执行**

```js
if (_busy > 0) → 报"还有操作在执行"
```

**因为 wrapper 在 execute 开头就 `_busy++` 了，它把自己算进去了。**

改成 `_busy > 1`。

**`\r` 混进字符串字面量**

2707 个 CR（我早先 Python 合并脚本的副作用）。`\r` 在 JS 里是行终止符，**单引号字符串里不能有它**。

于是报错指向**一行看起来完全正确的代码**，我对着它检查了三遍。

### 一个我不确定的地方

`desktop_resume` 的判断**依赖模型对用户话的理解**。

- 用户说"继续吧" → 我对了
- 用户说"你刚才在干嘛" → 我应该**不调**
- 用户说"算了" → 也该不调

**如果模型判错**，用户会看到一句"已解除急停（依据：…）"，然后可以**再按 ESC**。

**这是我目前能给的最好的办法** —— 它不假装自己知道用户的意思，只是把判断和执行都摊在明面上。
