## 2. B 项：完整性——汇报的解释不成立，但更接近真相了

### 汇报的说法

> 代码里没有"按路径推断完整性"的逻辑。同一份二进制报出不同级别，合理的解释是**父进程不同**。

### 我的对照实验（2.18.66，同一次 pwsh 调用内）

同一父进程（该 shell `whoami /groups` = **Medium**，S-1-16-8192）、三份**哈希完全相同**的 `dsc.exe`（`20BA9E94…`），只换位置：

| 位置 | `dsc.exe ping` 自报 |
|---|---|
| A. `profiles\desktop\node_modules\dsh-desktop-control\bin`（真实安装） | `integrity: Medium`, rid=8192 |
| B. **工作区内**（`.verify\dsc.exe`） | `integrity: Low`, rid=4096 |
| C. `%TEMP%` 下（新增的对照） | `integrity: Medium`, rid=8192 |

**同父进程、同文件、同一次调用**，只有位置不同 → 结果不同。所以"父进程不同"解释不了这个实验。

### 真正的机制（找到了）

```
icacls <工作区>                  → Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)
icacls <工作区内>\dsc.exe        → Mandatory Label\Low Mandatory Level:(I)(NW)     ← 继承
icacls %TEMP%\dsc-verify\dsc.exe → （无标签）
```

DSH 的 ACL 沙箱把**工作区目录标成 Low 完整性**（`(OI)(CI)NW`，便于受限令牌写入），**工作区里的文件继承该标签**；而 `%TEMP%` 下的副本没有标签。带 Low 标签的那份被启动时，进程实际就是 Low 完整性——这解释了"自报 Low 且拒绝写 `%TEMP%`"。

**所以你的代码确实是在读真实令牌**（这点汇报没错），但"同一份二进制只有父进程不同"的解释不对：**是文件/目录的完整性标签改变了子进程的实际级别**。

### 影响与建议

- **正常安装不受影响**（helper 在 profile 里，报 Medium）——体检脚本按 `pluginDir` 定位，正好避开这个陷阱。
- 但**任何把包解压到工作区再运行**的人（比如我这样的验收者、或想先试后装的人）都会看到 `Low` + 截图写不进 `%TEMP%`。汇报里把 `Low` 的文案改成"受限令牌，请在普通终端重跑"**是对的**，但对"工作区里的副本"这种情形会给出误导性的建议。
- 建议（低成本）：`ping` 里额外报告**自身文件是否带 Low 完整性标签**（或直接报 exe 路径 + 所在目录标签）。这既不加"按路径猜"的逻辑，又能让人一眼看出"哦，我在工作区里跑它"。

**修正后的结论**：B 的现象真实、机制是文件标签继承；汇报对*代码*的判断对、对*原因*的判断不完整。

## 8. 急停（ESC）+ `desktop_resume`：通过

操作者机器上 **ESC 键接触不良**，需要连按/伴随其它键才触发。这次**一次就触发了**，说明 hook 对"连按 + 伴随按键"的 ESC 是能识别的，不要求干净的单次按下。

完整时间线（用后台监视器以 500ms 间隔盯闸门文件）：

```
19:53:35  物理 ESC → 闸门写入
          halt 内容：「由物理 ESC 触发（dsc-esc 独立进程）2026-10-20 19:53:35」
19:53:43  监视器启动（此时已 halt=True）
19:53:49  尝试 desktop_move → 被拒：
          「Halted — 已被急停：闸门文件存在…拒绝执行 move」
19:54:18  halt True -> False   ← desktop_resume 生效
19:54:18  再次 desktop_move → 成功，光标回读 (660,400)
```

**拒绝提示写得很好**，直接阻止了 agent 的错误行为：

> **不要重试** —— 重试不会成功，只会让指示层反复冒出来，用户看起来像是插件不听他的。
> 也不要自行解除：急停是用户发起的，该由用户结束。

`desktop_resume` 的返回也如实标注了权限边界：**「这是你的判断 —— 如果用户其实没让你继续，他随时可以再按 ESC」**。

解除后 `esc.log` 显示指示层被重新拉起（新实例 hwnd=787912），符合"变更性操作会重新拉起指示层"的设计。

| 覆盖层窗口 | hwnd 动态创建，`94x96`~`96x96`，exStyle `0x80800A8`（**WS_EX_LAYERED + WS_EX_TRANSPARENT**），class=`Static` |

| 系统光标接管 | ✅ `fx.blanked` 写入 fx 的 pid |
| **停手后自动恢复** | ✅ 约 **22-25 秒**后 `fx.blanked` 清除（采样粒度 2s；文档写 30s，属同一量级） |
| **强杀 fx → 看门狗恢复** | ✅ 采样在 **429ms** 捕捉到进程已退出、随后 `fx.blanked` 清除；`guard.log`：`19:59:33.042 恢复光标（装饰进程 27940 已退出）ok=True` |

### 形状跟随：**确认成立**（作者文档没错）

为排除"插件调用本身写死姿态"的干扰，做了一次隔离实验：先触发一次操作让 fx 进入活动期，然后**完全不调用任何插件工具**，只用 `SetCursorPos` 移动真实光标：

| 光标位置 | 覆盖层位置 | 图像哈希 | fx.log |
|---|---|---|---|
| 记事本文字区 (700,450) | (678,390) | `46D8DB30C1CC` | 自行写入 `pose 2/0/3/4` |
| 菜单栏 (600,194) | (586,129) | `66102EEF2616` | 同上 |

**覆盖层跟着光标移动，两张图内容不同，且 fx.log 在没有任何插件调用时自己换了姿态** —— 说明 `dsc-fx.exe` 独立识别系统光标并选择对应素材。

> 补充说明（供作者参考）：`index.mjs` 里的 `fx.pose` 写入只是**动作提示**这一路输入；真正"跟随系统光标"的部分在 `dsc-fx.exe` 内部。我一开始只读了 `index.mjs`，据此得出"形状不跟随"的错误结论，已用上面的实验纠正。**文档的"形状跟着系统走"是准确的。**

### `yield(不认识的光标)`

`fx.log` 里出现过两次 `yield(不认识的光标)`。经实验确认这**不是缺陷**：遇到它不认识的系统光标类型时让出（显示系统原光标），属于合理兜底。建议在文档"已知限制"里加一句，免得用户以为光标坏了。

### 一条可用性建议（来自验收过程本身）

彩蛋的**运行状态只存在于真实 `%TEMP%\dsc-cursor-fx\`**，而 `desktop_diagnose` 完全没有这一节。后果：agent 想自查彩蛋状态（或想打开它，需往真实 `%TEMP%` 建标记文件）**只能绕开沙箱**，而"正常使用不该老翻沙箱"。

建议二选一：
- 把彩蛋状态（是否启用、进程 pid、`blanked` 状态、最近姿态）加进 `desktop_diagnose`；
- 或提供 `desktop_cursor_fx` 之类的开关工具（`desktop_indicate` 已有"操作指示层"的先例）。

## 11. 关于"翻沙箱"的说明（对作者有用）

本次验收有 5 处需要脱离 DSH 沙箱执行，**全部是我的取证动作，不是插件运行需要**：

| 需要的动作 | 为什么必须离开沙箱 |
|---|---|
| 读 `%TEMP%\dsc-cursor-fx\fx.log` / `fx.blanked` / `fx.pose` | agent shell 的 `%TEMP%` 被 DSH 重定向到 `dsh-XXXX`，插件的真实状态在沙箱内**不可见** |
| `tasklist` / `Get-Process` 查 `dsc-fx` | 沙箱内进程视图不全（实测会漏进程） |
| `taskkill` 强杀 fx | 制造故障测看门狗 |
| 跑 `smoke-report.mjs` | 脚本用管道捕获子进程输出，沙箱禁止 → EPERM |
| 往真实 `%TEMP%` 建 `dsc-cursor-fx.enable` | 开关文件在宿主真实 TEMP，不在工作区 |

**插件的正常使用（点击/截图/OCR/彩蛋启停）一次都没翻沙箱。**

如果希望"agent 能自查"而不必越权，最小改动是 **§9 那条建议**：把彩蛋状态并入 `desktop_diagnose`。
