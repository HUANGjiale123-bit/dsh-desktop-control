# dsh-desktop-control

> 让 AI 助手观察并操作 Windows 桌面：读窗口无障碍树、截图、点击、输入。
>
> **这会让 AI 操作你的真实鼠标和键盘。装之前请读完「风险」和「数据流向」两节。**

状态：**辅助进程可用，MCP 服务器可用，插件接入未完成。**

---

## 这是什么

一个 **MCP 服务器**（Model Context Protocol），把 Windows 桌面的观察与操作暴露为工具：

| 工具 | 只读 | 白名单 | 作用 |
|---|---|---|---|
| `desktop_list_windows` | ✅ | 不需要 | 列出可见窗口：标题、类名、进程、可执行文件、矩形 |
| `desktop_read_window` | ✅ | 不需要 | 读窗口无障碍树，元素带短 id 与物理像素矩形 |
| `desktop_screenshot` | ✅ | 不需要 | 截图存为 PNG，返回桌面原点坐标 |
| `desktop_click` | ❌ | **需要** | 在桌面绝对坐标点击 |

底层是一个独立的 Windows 辅助进程 `dsc.exe`：它在本机执行抓屏与输入注入，
MCP 服务器只负责协议翻译。

## 数据流向

**这一点必须看清：**

```
你的电脑
  ├─ dsc.exe        读你本机的窗口、无障碍树、屏幕像素
  ├─ MCP 服务器      在本机 stdio 上通信，不监听端口
  └─ 你的 AI 助手    把结果放进上下文
                        │
                        └──► 你配置的模型提供方   ← 这是唯一离开本机的环节
```

- **本程序自身不上传任何东西**：没有 HTTP、没有 socket、没有遥测，不做任何网络请求。
- **但截图与界面文本会进入 AI 助手的上下文，并随之发给你所配置的模型提供方。**
  屏幕上出现什么，模型就可能看到什么——包括误入画面的密码、私信、账户余额。
- 这是 computer use 这类功能的固有性质，不是本项目的缺陷。
  **如果你不能接受屏幕内容离开本机，就不要使用本项目。**

## 风险

- **它能点击、输入任何被白名单放行的应用**，包括浏览器、聊天软件、文件管理器
- **无障碍树与截图来自被操作的应用，属于不可信输入。** 恶意页面或应用可能在文本里
  藏指令，诱导助手点危险位置（提示注入）。本程序的工具结果带有显式标注，
  但**最终靠使用者的助手把界面内容当数据而非指令**
- **动作可能点错**：目标窗口可能已关闭、移位，或被别的窗口遮挡
- **打包应用（WinUI/XAML、CEF）几乎不暴露无障碍信息**，实测某 WinUI 记事本窗口
  整棵子树只有 12 个节点且全无名。此类目标只能走截图 + 坐标

## 安全模型

**Codex 式：应用白名单 + 操作前身份校验。**

- **白名单默认为空** —— 不显式放行，什么都操作不了。观察类工具不受限。
- 每次操作前重新枚举窗口，确认目标**仍然存在**，并校验其**可执行文件在白名单内**。
  这同时挡住"目标已关闭"与"句柄被复用"两种误伤。
- 白名单通过环境变量 `DSC_ALLOWED_APPS` 设置（逗号分隔的可执行文件名）：

```bash
DSC_ALLOWED_APPS=notepad.exe node server/server.mjs
```

**建议从最窄开始**：先只放行记事本这类无害目标，确认行为符合预期再放宽。
放行浏览器等于放行整个互联网——那是你的选择，但要知道它的含义。

## 怎么停下来

**`desktop_off` —— 本插件唯一的停止方式。** 它关闭状态指示层，并拉下急停闸门，
此后所有变更性操作被拒绝（观察类不受影响）。清闸门用 `dsc.exe stop --clear`。

### 关于「按 ESC 停」

**目前没有这个功能，代码里也没有留。** 原计划照 Codex 做一个物理 ESC 急停，
三条按键读取路径都试过并失败：

| 机制 | 实测结果 |
|---|---|
| `RegisterHotKey` | 注册返回成功，但永不触发（UIPI 静默拦截） |
| `WH_KEYBOARD_LL` 低级键盘钩子 | 安装成功，收不到任何按键 |
| `GetAsyncKeyState` 轮询 | 读不到按键状态 |

**但这里有一条重要的保留意见**：上面三次测试都是**从 sandbox 里启动的进程**做的。
本项目后来发现，"沙箱里不行"曾被错误地推广成"这台机器不行"——鼠标注入就是
这么被误判了整整一轮（见下面的历史注记）。所以**"ESC 收不到"这个结论同样
不能算定论**，它只证明了沙箱上下文里收不到，没证明宿主上下文里也收不到。

**要确认的话**：让宿主进程（而不是沙箱）拉起一个带 `WH_KEYBOARD_LL` 的程序，
然后在真实键盘上按 ESC。这个实验很便宜，我没有做过，所以这里不下结论。

代码目前不带 ESC：一个按了没反应的热键比没有热键更危险。如果上面的实验
证明宿主上下文里能收到，把它加回来是有价值的。

## 历史注记：一次把实现缺陷当成环境限制的误判

早期版本的 README 在这里写着「本环境阻断输入注入，这些工具只能用于观察」。
**那是错的。** 真实情况是两处实现缺陷：

1. 光标定位用 `SendInput` + `MOUSEEVENTF_ABSOLUTE`，其绝对坐标会被 DPI
   再缩放一次，落点恒为目标的 0.667 倍（= 96/144，本机 150% 缩放的倒数）。
   改用 `SetCursorPos` 后精确命中。
2. 文本输入用 `keybd_event(0, (byte)c, ...)`，`(byte)` 强转把中文截断成乱码。

两处都被"沙箱里 `SetCursorPos` 报错"这一次观察"解释"掉了，于是没人再去查。
**教训**：一次特定上下文里的失败，不能推广成一条关于环境的规律；把它写进
文档会让后来的人（包括自己）不再验证。

## 安全边界：白名单只做在插件层

**应用白名单（`DSC_ALLOWED_APPS`）由插件执行，helper 自己不检查。**

也就是说 `dsc.exe` 作为磁盘上的一个可执行文件，**直接运行时没有任何白名单
限制**，它可以操作任何窗口。插件层每次动作前会重新枚举窗口、确认目标仍存在、
并校验其可执行文件在白名单内；但这条防线不在二进制里。

在输入注入被误认为不可用的那段时间，这个缺口影响有限；**现在注入可用，
它的影响是实质性的**。如果你要把这套东西放到别人也能碰到的地方，第一件该做的事
是把白名单下沉到 helper 里。当前白名单为空时插件会拒绝一切操作，这是唯一的兜底。

## 安装与构建

```bash
git clone <repo>
cd dsh-desktop-control

# 1. 编译辅助进程（自动探测 csc.exe 与 WPF 程序集的位置）
cd helper && ./build.sh && cd ..

# 2. 启动 MCP 服务器
DSC_ALLOWED_APPS=notepad.exe node server/server.mjs
```

辅助进程的可用参数：

```bash
./helper/bin/dsc.exe ping                        # 自检：DPI 感知、CLR 版本
./helper/bin/dsc.exe list_windows
./helper/bin/dsc.exe tree <hwnd> [maxNodes]
./helper/bin/dsc.exe screenshot <hwnd> [outPath]
./helper/bin/dsc.exe click <x> <y> [right]
./helper/bin/dsc.exe click_element <hwnd> 'role=Button/name=保存' [right]
```

## 设计要点

两个 Windows 桌面自动化常见的坑，本项目专门绕开：

**坐标空间不一致。** UI Automation 返回的元素矩形可能是物理像素，而截图与像素校验可能
按逻辑像素工作；在 125%/150% 缩放设置下两者差一个比例，于是"读到的位置"与"点的位置"
对不上。

本项目的做法**不是去换算，而是让三个来源本来就一致**：辅助进程启动即调用
`SetProcessDPIAware()`，之后 Win32、UIA 与抓屏同处物理像素空间。截图返回 `origin`，
图内坐标加上 origin 即为桌面坐标——**全程只有平移，没有任何缩放**。

**元素寻址的类型细节。** 用 `PropertyCondition` 批量查元素时，某些属性要求特定数组
类型，传错即抛异常且信息不含上下文。

本项目改为：读取时给出稳定描述符（role / name / AutomationId），动作时按描述符重新
定位并点击其矩形中心。这同时解决了一次性进程模型下"上次的短 id 已失效"的问题。

完整的架构分析与调研记录见 [`docs/设计.md`](docs/设计.md)。
