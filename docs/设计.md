# DSH 桌面操控插件 — 实现计划

> 参照对象：OpenAI Codex 的 Computer Use（`@oai/sky` + `cua-repl`，已在本机拆解）
> 目标平台：Windows，本机（2240×1493 物理 / 1493×933 逻辑 / 150% 缩放）
> 状态：**计划待审，未开工**

---

## 一、从 Codex 抄什么（以及明确不抄什么）

### 抄：架构骨架

| 要素 | Codex 的做法 | 为什么关键 |
|---|---|---|
| **单一坐标空间** | 三件事在同一个原生进程里做 | 抓屏、取树、注入用同一套坐标，**结构上不可能错位** |
| **screenshotId 引用** | `click({ x, y, screenshotId })` | "点哪张图上的坐标"是显式指定的，不靠约定 |
| **树以字符串返回** | `tree` 是格式化好的字符串，元素 id 与命名动作内嵌 | JS 侧不解析不计算，只转发 |
| **原生 helper 独立进程** | `codex-computer-use.exe` | 桌面访问权在 helper，不在 agent 进程 |
| **ESC 物理急停** | 拦截记录写 `cache/computer-use/interrupts` | 用户随时能掐断动作 |

### 明确不抄

| 不抄 | 原因 |
|---|---|
| `js` 单工具 + JS 求值 | Codex 靠沙箱化的 `node_repl.exe` 保证安全；我若照做就得自己实现一个 JS 沙箱，风险与工作量都不可控。**改用独立工具面** |
| ChatGPT 后端依赖 | 那是它的托管服务，DSH 要的是本地自治 |
| Swift 版 helper（52 MB） | Windows 用不上 |
| 剪贴板句柄 / 拖拽句柄 / key_down-up / 音频录制 | MVP 不需要 |

### 关键纠正（本次调研得出）

**DPI 缩放不是障碍。** Codex 的 Windows 实现里搜不到任何 `dpi`/`scale`/`physical`/`logical` 字眼——它压根不换算。

`dsh-click` 之所以在 150% 缩放下全盘失效，根因不是"没做换算"，而是：

```
它把「读」（UIA 报物理像素）和「验」（抓图按逻辑像素裁切）分成两次独立抓取
→ 两次的坐标空间不一致 → 像素哈希永远对不上 → 每个动作都被自己拒了
```

**正确做法是不换算，而是"一次抓取、全程引用"（screenshotId）。**

## 二、架构

```
┌─────────────────────────────────────────────────────────┐
│ DSH 宿主进程                                             │
│                                                          │
│  插件（Cordis plugin，注册工具面）                        │
│     │                                                    │
│     │  每工具调用 = 一次 JSON 往返                        │
│     ▼                                                    │
│  常驻 helper 子进程  ◄──── 命名管道 ────►  插件           │
│  （桌面访问权在这一层）                                   │
│     ├─ 抓屏        → screenshots[] { id, data_url, filepath }
│     ├─ 取无障碍树  → tree（字符串，元素 id 内嵌）          │
│     └─ 注入输入    → 点击/输入/按键，同一套坐标            │
└─────────────────────────────────────────────────────────┘
```

**关键点：helper 常驻。** 因为要持有 `screenshotId → 坐标空间` 与 `element_id → 元素` 的映射，不能每次调用重启。

## 三、技术选型

### 方案 A：C# helper ★ 实测后改推这个

**已实测（本次会话）：**

```
dotnet SDK                          : 无（PATH 里没有）
.NET Framework csc.exe              : ✅ C:\WINDOWS\Microsoft.NET\Framework64\v4.0.30319\csc.exe
UIAutomationClient / Types 程序集   : ✅ 可加载
WindowsBase                         : ✅ 可加载
Roslyn（新语言特性）                 : 无
```

| 项 | 说明 |
|---|---|
| 优点 | Windows 无障碍与输入是原生一等公民；类型安全，`dsh-click` 那两个 bug 结构上不会犯；**不需要装 SDK**，系统自带编译器即可 |
| 缺点 | 只能用老 `csc`（C# 5 语言级别，无 `async/await` 之外的现代语法糖）；管道异步 I/O 要用 APM（`BeginRead`/`BeginWrite`） |
| 编译 | `csc.exe /target:exe /r:UIAutomationClient.dll ...` 一条命令 |
| 运行时 | 系统自带 .NET Framework 4.x，无需附加安装 |

### 方案 B：PowerShell 5.1 常驻助手

| 项 | 说明 |
|---|---|
| 优点 | 零编译、零依赖；系统自带 `UIAutomationClient`/`UIAutomationTypes` 程序集；`dsh-click` 已经证明这条路能读出完整的树 |
| 缺点 | 常驻 + IPC 要用 `NamedPipeServerStream`；PowerShell 的 UIA 对象模型比 C# 笨；`dsh-click` 就死在这条路上的类型细节 |
| 输入注入 | 需 P/Invoke `SendInput`（`Add-Type` 内联 C#）——本机已实测可行 |

### 方案 C：Node helper + 原生插件

| 项 | 说明 |
|---|---|
| 优点 | 与 DSH 同栈（Node）；`dsh-click` 本身是 Node 插件 |
| 缺点 | 抓屏与 UIA 需要原生模块（`koffi`/`ffi-napi`）或子进程，绕回方案 B 的问题 |

**我的倾向：方案 A（C#）。** 理由见下节实测结果——系统自带编译器，无需 SDK，且能拿到原生 UIA 与 `SendInput`。

**本次实测补充**：`dsh-click` 用 PowerShell 助手在记事本上成功读出 129 个元素（菜单、文档、状态栏、38 个标签页，带 `patterns: value/invoke/scroll`）。说明**取树这件事本身可行**，它是死在坐标与寻址——而那两处正是本计划要按 Codex 方式重做的。方案 B 因此降为备选。

## 四、传输与集成方式

Codex 用 MCP（`.mcp.json` 声明一个 stdio MCP 服务器）。DSH 这边的现状：

| 事实 | 出处 |
|---|---|
| `@deepseek-ai/dsh-mcp-client` 存在，但**未在 profile 启用** | `app.asar` 内 `/dsh/node_modules/`；`plugin_manager list_plugins` |
| `computerUse` 接缝存在且为空，只有一个 `register()` | `cordis_inspect_query` Service 目录 |
| 市场里有现成 MCP 管理插件 | `dsh-mcp-connector`(22,905)、`dsh-mcp-panel`(9,807)、`@hyzyn/dsh-mcp`(5,135)、`dsh-skill-mcp-panel`(4,528) |

**两条路，需你选：**

| | MCP 路线（照 Codex） | 原生插件路线 |
|---|---|---|
| 做法 | 启用 `dsh-mcp-client` + 配一条 stdio MCP 服务器指向 helper | 写成 Cordis 插件，注册 `computerUse` provider |
| 优点 | 结构与 Codex 一致；helper 可独立测试与复用；换 agent 也能用 | 不需要启用 MCP；直接进 DSH 工具面 |
| 缺点 | 要动 MCP 客户端配置，本 profile 未验证过 | 与 Codex 结构不同，将来不好移植 |

**我的倾向：MCP 路线。** 因为 Codex 的 helper 就是一个独立 MCP 服务器，照它做意味着助手层可以脱离 DSH 单独调试——而那正是最容易出错的一层。

## 五、工具面（MVP）

按 Codex 的 `FullDesktopComputerUseClient` 取舍，只做能闭环的：

| 工具 | 对应 Codex | 说明 |
|---|---|---|
| `desktop_list_windows()` | `list_windows` | 列出窗口：app / title / 坐标 / 尺寸 / 是否前台 |
| `desktop_window_state({ window, includeScreenshot })` | `get_window_state` | ★ **一次调用同时返回 tree 与 screenshot**，并给 `screenshotId` |
| `desktop_click({ elementId \| x,y, screenshotId, button, count })` | `click` | 坐标必须带 `screenshotId` |
| `desktop_type({ elementId?, text })` | `type_text` | |
| `desktop_press_key({ key })` | `press_key` | `Ctrl+S` 这类组合键 |
| `desktop_scroll({ elementId \| x,y, direction, pixels, screenshotId })` | `scroll` | |
| `desktop_launch({ app })` | `launch_app` | 按可执行路径启动，不走 shell |

**暂不做**：`drag`、`clipboard_*`、`key_down/up`、`move`、`move_relative`、`perform_secondary_action`、音频。

## 六、安全模型

Codex 用的是「应用白名单 + ESC 急停」。我打算在它之上加 DSH 原生的一层：

| 机制 | 来源 | 说明 |
|---|---|---|
| **应用白名单** | Codex 的做法（`~/.codex/computer-use/sessions/*.toml` 里 `allowed = ["illustrator.exe"]`） | 只有清单内的应用可被操作 |
| **每次动作过 `ctx.approval`** | dsh-click 的正确部分 | 用 DSH 官方审批接缝，不自己造 |
| **ESC 物理急停** | Codex | 助手监听 ESC，一旦按下即中断并写入拦截记录 |
| **不抢前台焦点** | dsh-click 的正确部分 | 默认不 `activate_window`，避免打断你手头的操作 |
| **脱敏** | dsh-click 的正确部分 | 树文本与截图路径进模型前截断、掩码 |
| **审计事件** | dsh-click 的正确部分 | 观察与动作写入会话日志 |

**这一层是"Codex 架构 + dsh-click 的安全面"的混合**——你选的是参照 Codex，但 Codex 的安全模型比 dsh-click 薄（它靠白名单 + ESC，没有逐动作审批），所以我建议把 dsh-click 那部分安全设计保留过来。**这一条需要你确认。**

## 七、风险与未知

| # | 风险 | 严重度 | 缓解 |
|---|---|---|---|
| 1 | **截图吃上下文**。一张 1000×688 图就不小，频繁截会烧额度 | 高 | 工具面强制"树优先、截图可选"；`includeScreenshot` 默认 false；只在必要时截 |
| 2 | **动作后不settle**。点完立刻读状态可能读到旧的 | 中 | helper 内置 `action_settler` 等价物（Codex 在 Linux 侧有 `action_settler.js`） |
| 3 | **元素寻址的类型坑**。`dsh-click` 死在 `AutomationElementIdentifiers.RuntimeIdProperty` 的 `PropertyCondition` 类型上（实测报错：`值必须为 "Int32[]"`） | 中 | 不用 `PropertyCondition` 做批量查找；改用 `TreeWalker` 遍历时记录每个元素的 `RuntimeId`，或直接持有 `IUIAutomationElement` 引用存表 |
| 4 | **C# 语言版本受限**。系统只有老的 `csc.exe`，无 Roslyn | 低 | 用 C# 5 语法写；异步管道用 APM（`BeginRead`/`BeginWrite` + 回调）而非 `Task` |
| 5 | **命名管道** | 低（已部分验证） | **已实测：服务端创建 ✅ → 客户端 `Connect` ✅ → 服务端确认连接 ✅**。连接后的数据分帧在我的 PowerShell 测试脚本里没跑通（编码与构造函数踩坑），但那是我测试代码的问题；真 helper 用 C# 写，管道 I/O 是原生能力。**仍列为阶段 1 的第一件事** |
| 6 | **提示注入**。树文本来自被操作的软件，是不可信内容；恶意文本可能诱导我点危险位置 | 高 | 白名单 + 逐动作审批 + 树文本标注为数据；我自己也必须把它当数据不当指令 |
| 7 | **点错窗口**。目标窗口可能已关闭或移位 | 中 | 每次动作前校验窗口身份（pid + 可执行路径），变了就拒 |
| 8 | **Codex 的 Windows 实现只有三个 JS 文件**，说明重活全在原生 exe 里，而那个 exe 我不能反编译复用 | — | 接口我照抄，实现我自己写 |

## 八、验证标准（做到这条才算成功）

**唯一验收标准：**

> 在 150% 缩放下：
> 1. `desktop_window_state` 读出记事本的树 + 截图，给出 `screenshotId`
> 2. 从树里取一个元素的 `element_id`
> 3. `desktop_click({ elementId })` 点中它
> 4. 再读一次树，**确认点中了**（状态变化可见）

**这一条过了，剩下的都是体力活。过不了就是又一个 `dsh-click`。**

**次要验证**：截图路径的坐标可信——即"我按截图上看到的 (x,y) 去点，确实点在那里"。

## 附：本次调研产出的实测事实（备查）

| 结论 | 证据 |
|---|---|
| 宿主派生的子进程**有桌面输入权** | 提权后 `SetCursorPos` 返回 `True`，光标从 (1023,664) 移到 (300,500) |
| 宿主派生的子进程**能建命名管道并建立连接** | `serverCreated=true` → `Connect` 成功 → 服务端 `IsConnected=True` |
| 沙箱会同时掐掉输入注入与管道连接 | 非提权下 `SendInput` 返回 0、`Connect` 报 `Access to the path is denied` |
| Codex 的 computer use **不需要处理 DPI** | Windows 实现三个 JS 文件里搜不到 `dpi`/`scale`/`physical`/`logical` |
| Codex 的坐标空间**靠 screenshotId 钉住** | `click`/`scroll`/`drag` 签名均含 `screenshotId` |
| 本机显示缩放为 150% | 物理 2240×1493 / 逻辑 1493×933；真实窗口 574×789 → UIA 报 861×1184（×1.5） |
| `dsh-click` 的树读取本身是好的 | 记事本上读出 129 个元素，含 `patterns: value/invoke/scroll` |
