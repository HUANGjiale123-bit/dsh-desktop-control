## 一、未解的问题

### 1. 鼠标注入完全无效（最严重）

**现象**：`SetCursorPos` 与 `SendInput`（相对 / 绝对 / 绝对+VIRTUALDESK）全部无效。
判据是**读回光标实际位置**，不是返回值：

```
起始光标 = (2111,579)
目标(400,300)   → 实际(2111,579)  ❌
目标(900,500)   → 实际(2111,579)  ❌
目标(1400,800)  → 实际(2111,579)  ❌
目标(600,200)   → 实际(2111,579)  ❌
目标(1100,900)  → 实际(2111,579)  ❌
目标(300,400)   → 实际(2111,579)  ❌
到达 0/6
```

**已排除**：桌面身份（WinSta0\Default，与 `OpenInputDesktop` 同名）、会话（同为 44）、
作业对象 UI 限制（`UIRestrictionsClass = 0`）、AppContainer、提权（所有进程都是
ElevationType=3 Limited）、`BlockInput`、DPI（awareness 生效，屏幕读作 2240x1400）。

**间歇性证据**：同一段代码、同一台机器，在某些时刻有效（实测过 `SetCursorPos(400,300)`
命中、按钮被点击 4 次），在另一些时刻完全无效。**触发条件未确定。**

**一个未验证的对照**：Codex 也用 `SendInput`，用户认为它能操作鼠标，但**实际上没有验证过**
——用户的原话是"叫他直接开启这个功能，他说开启了，但我的屏幕和鼠标都没有反应"。
所以 Codex 的鼠标很可能也动不了。**这个对照值得做一次**：让 Codex 执行一个明确需要
移动鼠标的动作，肉眼确认光标是否移动。

### 2. 键盘注入在 Electron 应用上无效（待确认）

**现象**：往 DSH 自己的输入框注入 `"XYZ123"`，命令返回 `typed=6`，
**截图显示输入框是空的**（只有占位文字）。

**但结论不确定**，因为我说不出这两者的区别：

```
树里没有输入框  →  Electron 默认关闭无障碍？
                →  还是字没送进去？
```

**而且更可能的解释是：我只激活了窗口，没把焦点放进输入框。**
再点击输入框那一步失败了（因为问题 1），所以焦点始终没到位。

**验证方法**：在 Chrome/Edge 的地址栏里试——那是普通 Win32 窗口的子控件，
如果键盘能进地址栏但不能进 Electron 的输入框，结论就清楚了。

### 3. 同一段代码，点自己的测试窗口成功、点真实应用失败

```
✅ WinForms 测试窗口（我编译的）→ click_element 成功，按钮文字 "点了 4 次"
❌ 记事本（WindowsApps 打包）  → SetCursorPos 失败
❌ 腾讯视频（Electron）        → SetCursorPos 失败
❌ DSH 自己（Electron）        → SetCursorPos 失败
```

**令牌特征完全相同**（都是 `提升类型=3`、非 AppContainer、同会话），
所以不是完整性级别差异。**未解。**

## 三、我自己的方法错误（教训）

这几条导致的返工比技术问题本身更多。

### 1. 把"返回值"当"效果"

`desktop_type` 返回 `{"ok":true,"typed":6}` 只说明**我发出去了**，
不说明**字到了**。补上读回验证之后才第一次真正区分开这两种情况。
（用户早就提示过"没看你动鼠标"，我当时没领会。）

### 2. 读不设置 last-error 的 API 的错误码

`SetCursorPos` **不设置** last-error。我却在它后面调 `GetLastWin32Error()`，
于是读到的是**上一个 API 留下的陈旧值**：`2`、`203`、`0`、`5` 都出现过。
**我据此报过三个不同的"根因"，全是假的。**

**判据应该是"光标实际位置"，不是错误码。**

沙箱里 `SetCursorPos` 报过一次 `ERROR_FILE_NOT_FOUND`，我把它写成

### 4. 只在自己造的窗口上验证

## 八、Codex 复核后的修正（2026-10-14）

用户把代码包交给 Codex 复核，它在同机同会话（Session 44）直接复现了问题 1，
并指出本文档若干处错误。**以下三条必须按它的结论修正。**

### 修正 1：「已排除 AppContainer」是错的

本文档第一节写着"已排除 AppContainer"，**依据是错的**。

我的诊断程序 `TargetProbe.cs` 打印的是**被探测进程**的令牌特征，
而且它能对目标进程成功调用 `OpenProcessToken`。**在 AppContainer 进程里打开
非 AppContainer 进程会被拒绝** —— 所以"能拿到完整令牌特征"这件事本身说明：
跑诊断的那个进程不在 AppContainer 里，**它看不到失败时的上下文**。

**要查的是注入方自己的 `TokenIsAppContainer`，而且要在失败的那一次运行里查。**

Codex 在它的环境里测到 `IsAppContainer = 1`，并判定：
**AppContainer 进程被系统禁止向交互式桌面注入输入**，这是问题 1 的最可能根因。

它同时解释了间歇性：**进程是否在 AppContainer 里，取决于它是从哪儿启动的**。
从 Codex 会话的终端启动 → 在沙箱里 → 注入无效；从普通快捷方式启动 → 不在 → 正常。

再叠加一条时间线证据：Codex 沙箱在 10/13–10/14 之间变化过
（`cua_node` 运行时从 `cfb32733c877621e` 换成 `b474a88d5d105afa`，
`[windows] sandbox = "elevated"`），与"早先有效、后来完全无效"吻合。

**边界说明（Codex 自己强调的）**：它在 AppContainer 内部无法构造对照组，
所以"AppContainer 是唯一原因"是**最强假设，不是已证因果**。
证据是"除它之外全部正常 + 症状完全一致"。

**我这边实测**：本 shell 与 explorer、DSH 的 `IsAppContainer` 都是 **0**，
所以**本机这条不成立**——我的问题 1 另有原因，或与 Codex 环境不同。

### 修正 2：CompareObjectHandles 可以用，是我导错了 DLL

| 模块 | 是否有 CompareObjectHandles |
|---|---|
| `kernel32.dll` | **没有**（但 `CreateFileW` / `GetLastError` / `IsProcessInJob` 都在，导出表正常） |
| `kernelbase.dll` | **有** |
| `api-ms-win-core-handle-l1-1-0.dll` | **有** |

新版 Windows（本机 10.0.26200）的 kernel32 越来越薄。**改成
`DllImport("kernelbase.dll")` 即可。**

**顺带纠正一个推理错误**：我曾从 `GetThreadDesktop=300` 与 `OpenInputDesktop=696`
句柄数值不同，推出"输入不在那个桌面上"。**这个推理不成立** ——
Codex 实测 `0xDC` vs `0x890` 用 `CompareObjectHandles` 判定为**同一对象**。
后面那次 `SetThreadDesktop` 实验，是在追一个用错判据得出的假设。

### 修正 3：「低层键盘钩子在本机不通」被证伪

用户本机上 **Codex 的 ESC 急停是有效的**，而 Codex 的 ESC 就是低层输入钩子
（`src/input/interruption.rs`、`LowLevelInputHook`、`SetWindowsHookExW` +
`MsgWaitForMultipleObjects(input hook)`；两个二进制里 `GetAsyncKeyState` /
`GetKeyState` / `RegisterHotKey` 都是 0 命中）。

**所以同一台机器上低层键盘钩子能收到物理按键。** 我的钩子不回调，
候选原因仍是那几条：装钩线程 ≠ 泵消息线程、`PeekMessage` 按 hwnd 过滤、
钩子线程被饿死静默摘钩、`dwThreadId` 传了非 0 —— **或者同样是因为在 AppContainer 里**。

### Codex 确认我说对的

- `SetCursorPos` 不设置 last-error，之后读 `GetLastWin32Error()` 拿到陈旧值 —— 正确
- 判据要用"光标实际位置"而不是返回值 —— 正确
- 真实应用 UIA 树都是残的、只有截图能看 —— 与 Codex 侧设计一致
  （`include_text` 默认 false、`include_screenshot` 默认 true）
- `SetThreadDesktop` 那次"更糟"的现象可信，但**当时的前提是错的**，
  不能据此否定这个 API

### 本轮据此做的修改

| 修改 | 依据 |
|---|---|
| 鼠标按键从 `SendInput` 改为 `mouse_event` | Codex 的脚本实测：同一环境里 `SendInput` 相对移动 ret=1 但无效，`SetCursorPos` ret=True 且**真的移动**。两者走不同路径，鼠标按键应与 `SetCursorPos` 同路 |

**验证**：改后测试窗口连点 5 次全部成功（按钮文字 `点了 5 次`）。
**但记事本仍然失败** —— 说明问题 2 是独立于本条的另一个原因。

### Codex 建议的下一步

1. 跑它写的 `dsh-injection-truthcheck.ps1`，在失败环境与普通窗口各跑一次，
   对比 `IsAppContainer` 与注入真伪
2. 定案后在 helper 启动时加自检：`TokenIsAppContainer` 为 1 就直接报错退出，
   **别让"注入静默无效"再伪装成环境限制**
3. 「让 Codex 移动鼠标、肉眼确认」这个对照**暂时做不了**：

   + `SKY_CUA_NATIVE_PIPE`，当前没有 helper 进程在跑）

```
  SendInput 相对(+40,+40) ret=0 → 位移(0,0)
  到达 0/3
```

### 关键差异在光标读数上

| 谁 | 起始光标 | 说明 |
|---|---|---|
| 我的 shell | **(1059,1143)** | 在交互式桌面上，读得到真实位置 |
| Codex 的 shell | **(0,0)** | **看不见桌面** |
| Codex 的 computer use helper | — | **注入成功**（实测移动了光标） |

### Codex 的解释

> Computer Use 能真的移动鼠标，是因为它的 helper（`codex-computer-use.exe`）
> 是**独立进程，不在我这个 shell 的沙箱里**。

### 由此得到的结论

**shell 进程处在一个"能读、不能注入"的受限上下文里。**
真正能注入的进程必须在这个上下文之外——Codex 的 helper 就是这样的进程。

**这同时解释了我这边的现象**：我的 helper 是 shell 的子进程，
继承了同样的受限上下文，所以五种注入方式全部无效。

### 另一个观察：Codex 也起不来我的程序

Codex 报告：从原路径 `tools\diagin` 直接启动时进程起不来，
**退出码 `0x8007045A`（DLL 初始化失败）**，复制到它的工作目录后才能跑。

这与"受限上下文"一致——它也没能在我这边的目录里正常加载。
