## 1. 五个 P1：逐条答复

### P1-1 region 子矩形时坐标二次映射

- **现状**：候选点（整图像素）与报点（裁图内 u/v）分成两条换算：
  `candidatePointToWindow()` 与 `viewPointToWindow()`，按 `source` 分流。
- **证据**：评审给的反例 `(1200,400)` 固化成单测；工具边界断言（见 §4）证明
  真实调用里传的是 `desktop` 空间且落点 = 窗口原点 + 图内锚点。

### P1-2 基线取自新屏幕，掩盖 T0→T2

- **现状**：撤销"从屏幕取基线"，回到**OCR 实际读的那张 PNG**；
  删掉"每个候选抓一次屏幕"，列表不再起 N 个 helper。
- **证据**：`test-visual-recheck`（自造变脸窗口）拒绝 + 光标未移动；`test-visual-tools` 正常点击放行。

### P1-3 登记发生在 await 之后

- **现状**：算完 → 最后一次有效性检查（记录/代次/闸门/归属）→ **同步一次性提交**，
  提交段内没有 await；`ownerId` 在入口固定。
- **证据**：`test-visual-barrier` —— 2 秒慢 OCR 期间用真实动作作废观察，返回必须
  "观察失效且未登记"，再拿可能的 candidateId 点击必须找不到。

### P1-4 命中词却点行中心

- **现状**：`matchWordRun()` 按连续词匹配，用**命中词的并集框**；一行两个目标给两个候选；
  `win-ocr.ps1` 的行并集改成对所有词求 min/max。
- **证据**：单测覆盖跨词命中与整行退化。

### P1-5 OCR 同步阻塞

- **现状**：`execFile` 异步；语言探测并进同一次启动（`-ProbeOnly`），不再开两个 PowerShell。
- **证据**：返回里同时给"识别耗时"和"进程往返"（实测 104ms / 593ms）。

## 2. 那个"同像素不同指纹"的最终结论

**是 `LockBits(rect)` 取子矩形时不可靠**，不是像素问题。

- 改成"锁整图 + 按 `rect.X/rect.Y` 偏移"后，两种取法给同一指纹：`3d0af0c36208cf36`。
- 我之前的两次"验证"都是错的，已写进文档当反面教材：
  1. 探针用的是 `tempHelper()` 缓存的**上一次构建**的二进制；
  2. 用 Pillow `getbbox()` 判断"完全相同"——它默认 `alpha_only=True`，
     alpha 相同时连 RGB 差异都报 None（评审提醒得对）。
     改用 `getbbox(alpha_only=False)` + `tobytes()` 复核后，才确认这次是真相同。
- 新增**纯文件测试**（评审 §6 建议）：`test-hash-crop` 覆盖 1/3/7/17/171 五种
  不整齐宽度、非零原点、32bppArgb 与 24bppRgb，大图子矩形必须等于独立裁出的 PNG。

## 3. 容差：从猜的到测的

新增 `image_diff`（两张 PNG，不碰屏幕）+ 构造好的 8 组样本对
（PASS：原图/±1/±2/单列+1 接缝；REJECT：改字/位移 2px/遮挡条/整体变暗 8/勾选框多一道勾）：

```
容差 | 误拒 | 漏放 | PASS 最大差异像素 | REJECT 最小差异像素
  0  |   3  |   0  |      8418        |       28
  1  |   1  |   0  |      8418        |       28
  2  |   0  |   0  |         0        |       28   ← 出厂
  3  |   0  |   0  |         0        |       28
  4  |   0  |   0  |         0        |       28
  6  |   0  |   0  |         0        |       28
  8  |   0  |   1  |         0        |        0
 12  |   0  |   1  |         0        |        0
 20  |   0  |   1  |         0        |        0
```

三条结论都写进了代码注释：

1. 容差 0 **一定误拒**（3 个纯噪声样本）——"纯等价比不了"的量化证据；
2. **安全带 2..6**，取出沿 2：漏放（点击送进已变的界面）比误拒（重看一眼）贵；
3. **容差 8 开始漏放**：那道勾的最大通道差只有 **7** —— 小但重要的变化存在，容差不能一路放大。

## 4. 第二批：裁图放大 + 模型报点

- `dsc.exe crop`：裁 + 整数倍放大（NearestNeighbor，避免糊边假清晰）。
- `desktop_visual_view`：把一块区域放大后**作为图像**交给模型，返回 `viewId`，
  并列出区域内 OCR 文字及其 `(u,v)` 供目测对照。
- `desktop_click_candidate(viewId, point:{u,v})`：模型报点，插件换算；
  走与候选**完全相同**的复查/几何/白名单/急停/落点链。

**工具边界断言**（评审 §10-1 原话：要在边界拦截传给 `set.tools.click` 的参数）：

```
✓ 捕获到真实调用：{"x":1589,"y":188,"space":"desktop"}
✓ 落点与"窗口原点 + 图内锚点"一致（期望 1589,188，实际 1589,188）
✓ 带上了 expectedGeom（688x1055）
✓ 报点 u=0.5,v=0.5 落在裁剪区中心（期望 1783,588，实际 1783,588）
```

实现方式：`apply()` 把 toolset 经 `getToolsetForTest()` 交给测试（宿主不读），
测试包装 `set.tools.click` 记账再转发。

```json

 "ocrInput":"crop","ocrBackend":"windows-ocr","engineLanguage":"zh-Hans-CN",

 "beforeImage":"…png","afterShotId":"…","afterImage":"…png",
 "imagePoint":{"x":413,"y":508},"windowPoint":{…},
 "desktopPoint":{"x":636,"y":647},
 "recheck":{"diffPixels":0,"total":2548,"maxDelta":0,"tol":2},"roi":{…}}
```

## 6. 顺手修掉的真问题（都是真实使用才暴露的）
