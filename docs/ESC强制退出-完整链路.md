# ESC 强制退出：完整链路与踩过的坑

**日期**：2026-10-15
**状态**：端到端验证通过（七步全绿）

---

## 这套东西解决什么问题

**鼠标可以被恶意程序抢**——抢焦点、全屏覆盖、伪造点击、占住光标。
**键盘抢不了**——低层键盘钩子在系统把按键投递给任何窗口之前就能看到它。

所以"点按钮停"只是方便，**"按物理 ESC 停"才是保险**。
这是 ESC 存在的理由，不是可有可无的附加项。

---

## 完整链路

```
插件 desktop_indicate
   ├─ 拉起 dsc-edge.exe  →  屏幕四边的蓝色粒子光带
   └─ 拉起 dsc-esc.exe   →  屏幕上方逃生条 + 唯一的 ESC 钩子
                            （两者共用同一个消息循环/进程）

用户按物理 ESC
   └─ dsc-esc 的钩子捕获 vk=0x1B
        ├─ 写闸门文件 <工作区>\.desktop-control\halt
        └─ 自己退出

dsc-edge 每 500ms 查看闸门
   └─ 发现闸门 → 自己关闭 → 界面消失

dsc.exe 每次变更性操作前检查闸门
   └─ 闸门存在 → 拒绝执行（"已被急停"）
```

**闸门是全局唯一的事实来源。** 三个程序都靠它对齐，不靠进程间通信——
文件存不存在不会像通道那样断开。

### 两条关闭路径刻意不同

| 触发方式 | 闸门 | 为什么 |
|---|---|---|
| **ESC / 逃生条** | 拉下并**保留** | 那是"别再动我电脑"的持久表达，之后的操作用户按说就该被拒 |
| **desktop_off**（助手正常收工） | 拉下后**随即解除** | 正常关闭不该留一道永久封锁，否则下次操作被拒时用户以为是插件坏了 |

## 踩过的坑（都是"看起来合理但实测不通"）

### 坑一：低层键盘钩子需要宿主进程有一个**可见且被激活过**的窗口

四种形态的实测对比，同一套钩子代码：

| 宿主形态 | 回调次数 |
|---|---|
| 完全没有窗口 | **0** |
| 隐藏的哨兵窗口 + 手写 `GetMessageW` 循环 | **4 次后彻底停止** |
| 隐藏窗体 + `Application.Run` | **0** |
| **可见窗口 + 至少激活过一次** | **稳定触发** ✅ |

**关键细节**：激活过一次之后，**焦点切到哪都无所谓**——实测切到别的窗口再按 ESC 照样触发。

**为什么这个坑特别贵**：我据此两次得出"这台机器不支持键盘钩子"的结论，
两次都是错的。真正的原因是窗口从没被点过——**而代码看起来完全正确**。

**最终设计正好化解了它**：逃生条本来就要显示，它自己激活一次（300ms 后
释放焦点），前提自然满足。

### 坑二：先把 ESC 判定放在记日志之后

原顺序是"先 `Log(...)` 再判断 ESC"。而 `Log` 里的 `Console.Error.WriteLine`
在宿主用 `2>&1` 重定向启动时会抛异常，冒泡到钩子回调的外层 catch，
**整个回调报废，ESC 分支根本执行不到**。

症状：钩子装上了、按键也真按了、就是没反应——与"钩子不工作"完全无法区分。

**规则**：判定路径不许碰 IO。想一下"把日志功能整个删掉，急停还工作吗"。

### 坑三：分层窗口 + TransparencyKey 渲染成全透明

全屏逃生窗用 `WS_EX_LAYERED` + `TransparencyKey` 时，
`IsWindowVisible` 返回 **True**、窗口矩形正常（`(0,0 1493x933)`），
**但屏幕上什么都没有**。

**逃生窗不能依赖这条渲染路径**——它最不能承受的就是"隐身"。
现在是普通窗口，渲染路径只有一条。

### 坑四：闸门位置猜错了三次

| 选的位置 | 为什么不行 |
|---|---|
| `process.cwd()` | DSH 宿主的工作目录是 **profile 目录，只读** |
| 环境变量 | DSH **没有** `DSH_SESSION_WORKSPACE` 这种东西，工作区是会话概念 |
| 插件自己的目录 | npm 装到 `profile/node_modules`，**也不在工作区** |

**为什么必须放工作区**：`dsc.exe` 是沙箱子进程，**只能写工作区**。
实测往 profile 目录写直接 `UnauthorizedAccessException`。
而 `dsc-esc` 由宿主直接 spawn、没被沙箱套住，哪都能写——
**位置要迁就权限更小的那一方**。

**正确做法是问 DSH**：

```js
ctx.get('workspaceRegistry').list()
  → 每个 workspace 带 path 和 sessionIds
  → 用 currentInitiator().id 反查
```

### 坑五：问得太早（这个最隐蔽）

反查逻辑写对了、服务拿到了、数据里确实有本会话 id——**但结果还是错的**。

原因：`agents.currentInitiator()` 是**工具调用期间**才建立的进程内因果链，
插件 `apply` 的时候还没有会话，取到 `undefined`，于是永远走兜底分支。

**改法**：惰性求值——第一次真正要用闸门时才算，并缓存。

**为什么这个坑值得单独记**：服务存在、数据存在、会话 id 在列表里，
**代码审查看不出来任何问题**，唯一错的是"问的时机"。

### 坑六：两个程序各装一套钩子

`dsc-edge` 和 `dsc-esc` 都装了低层键盘钩子。两套都能工作，
但一次 ESC 只会被其中一套抓到——**"到底谁负责停止"变得含糊**。

现在职责拆干净：`dsc-edge` 只画光带，`dsc-esc` 独占钩子 + 逃生条。

**拆开后的新问题**：两者失去联系——ESC 让 `dsc-esc` 退出并写闸门，
而光带不知道，**继续挂在屏幕上**。用户看到的是"按了 ESC 没反应"，
**而操作其实已经停了**。

这比真没停更糟：它让一个正常的保险机制看起来是坏的。
**修法**：光带每 500ms 查看闸门文件，出现即自行关闭。

## 排查这类问题的通用教训

**今天我在同一个错误上栽了四次**：把自己的测量方式错误当成环境限制。

| 表面结论 | 真实原因 |
|---|---|
| "这台机器阻断输入注入" | exe 放在名为 `dsh workspace` 的目录里 |
| "键盘钩子不触发" | 窗口从没被激活过；日志写进了只读位置 |
| "日志丢失/程序秒退" | 沙箱不让写工作区外，异常被吞 |
| "闸门拦不住操作" | 我直接跑 `dsc.exe` 没带 `DSC_HALT_GATE`，它找的是默认路径 |

**规则**：得出"环境不行"的结论之前，先用一个**最小可复现程序**把变量压到只剩一个，
并且**让别人（或另一个进程）跑一遍同样的东西**做对照。

**另一个规则**：改完代码后要能**确认跑的是新代码**。
DSH 会缓存已加载的插件模块，磁盘上的文件对了、内存里的可能是旧的——
唯一症状是一句看起来像代码 bug 的报错。所以诊断工具里带了版本号和构建标记。

## 怎么自检

```
desktop_diagnose          # 只读：版本、闸门路径、各程序位置、准入状态
```

它会打印闸门路径的**完整解析过程**——服务取没取到、会话 id 是什么、
注册表里有哪些 workspace、反查命中没有、最终路径是什么。
闸门位置不对时，症状完全一样（ESC 关界面但拦不住操作），
只有把中间层打出来才分得清卡在哪一步。
